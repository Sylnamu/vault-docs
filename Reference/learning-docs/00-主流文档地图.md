# 主流文档地图（L2 Team 级 · TS+Node 假设 · 主案例 vercel/next.js）

> 讲解中文 / 模板英文。目标：给你一把量任何 GitHub 仓的尺子。

## 0. 你的关注点叫什么（正名）

你说的 agents.md、tech、product，在主流里叫：

| 你说的 | 主流叫法 | 一句话 |
|---|---|---|
| agents.md | **AGENTS.md / Agent collaboration contract**，Docs-as-Code 的一种 | `README for agents`：告诉 Agent/新人怎么构建、测试、提 PR。标准见 https://agents.md/ |
| tech | **Contributor docs + Technical docs**：`ARCHITECTURE.md / CONTRIBUTING.md / ADR / Reference` | 给贡献者/维护者看的。理论底座是 **Diátaxis** https://diataxis.fr/ + Google《SWE Book》Ch.10 https://abseil.io/resources/swe-book/html/ch10.html |
| product | **User docs + Product docs**：`docs/ / UPGRADING.md / CHANGELOG / PRD / ROADMAP` | 给用户/需求方看的。输入输出流水线是 Conventional Commits → SemVer → Keep a Changelog |

以后接轨就说这三句，不用再模糊描述。

## 1. 核心模型：3 读者 × 4 象限

### 1.1 读者矩阵（谁看）

```
给用户看 (User)        → docs/ + errors/ + UPGRADING.md + Releases + README.md（薄）
给贡献者看 (Contributor) → CONTRIBUTING.md + ARCHITECTURE.md + decisions/ADR + .github/ 流程
给 Agent 看 (Agent)      → AGENTS.md + .github/AGENTS.md + skills/ + packages/*/README
```

**next.js 的分界规则（真实）：**

* 用户永远被赶出仓库：`readme.md` 全文指向 `nextjs.org/docs`（即 `docs/*.mdx` 渲染结果）；报错 CLI 里直接链到 `errors/*.mdx`（100+个）；升级只留 `UPGRADING.md` 2行跳转；更新日志不在仓内，在 GitHub Releases。
* 贡献者留在仓库：`contributing.md` 是薄索引，分 `core/ docs/ repository/ turbopack/` 四象限 + `AGENTS.md` 执行手册。
* Agent 看三层：`AGENTS.md`（常驻 guardrail：monorepo地图/pnpm矩阵/4种测法/secrets红线）→ `.agents/skills/*`（21个深潜工作流，按 `$name` 调用）→ `.github/AGENTS.md`（只讲 CI 安全：permissions最小化、Action pin到SHA、防注入）。

演进点：`CLAUDE.md / .cursorrules` 单文件模式在 next.js 已被 `skills/` 目录取代。这是 AI 原生仓趋势，L2 你先用单 `AGENTS.md`，L3 再拆 skills。

### 1.2 Diátaxis 四象限（写什么）

写前先问：读者是来**学 / 做 / 查 / 懂**？

* Tutorial（学习导向，手把手）→ `docs/tutorial-getting-started.md`
* How-to（任务导向，解决具体问题）→ `docs/how-to-upgrade.md`，`errors/*.md`
* Reference（信息导向，查阅）→ `docs/reference-api.md`
* Explanation（理解导向，讲为什么）→ `docs/explanation-*.md` + `ARCHITECTURE.md` + `decisions/ADR-*`

一个文件只做一类，混写必败。next.js 的 `docs/01-app/01-getting-started/ + 02-guides/ + 03-api-reference/` 就是这套的落地，另加数字前缀排序 `01-app/02-pages/03-architecture/04-community`。

## 2. 三级规模（为什么重点 L2）

* **L1 Starter（个人，3件）：** `README.md + AGENTS.md + CHANGELOG.md`。不写就翻车：换电脑跑不起来、Agent 乱改脚本、无版本号。
* **L2 Team（小团队，约12文件，本骨架）：** L1 + `ARCHITECTURE + CONTRIBUTING + UPGRADING + docs/4件 + decisions/ADR + product/PRD+ROADMAP + .github/模板`。解决 next.js 里真实出现过的问题：trivial PR 泛滥（所以 contributing 声明 typo PR 大概率关）、报错找不到出处（所以 errors 按码建档）、升级骂声（所以 UPGRADING 单列）。
* **L3 Scale（大仓治理）：** L2 + `RFC流程 + CODEOWNERS + .agents/skills/ + 发版通道文档 + 多包 README`。next.js 的 `contributing/repository/release-channels-publishing.md + CODEOWNERS + 21个skills` 就是 L3。

## 3. L2 每个文件：何时写 + 不写翻车 + next.js 对照

| 文件 | 读者→作者 | 何时写 | 不写翻车（GitHub 真实情景） | next.js 对照 | 权威 |
|---|---|---|---|---|---|
| `README.md` | 用户→维护者 | 建仓第一天，保持薄 | 写成大杂烩，用户找不到官网/示例 | `readme.md` 全小写、只讲是什么+跳转 | — |
| `AGENTS.md` | Agent/新人→维护者 | 引入 AI/第二人前 | Agent 用 npm 而你用 pnpm，CI 全红；secret 被提交 | 根 `AGENTS.md`：build矩阵/4种测法/worktree/fork-PR区别 | https://agents.md/，嵌套就近优先，32KiB截断 |
| `ARCHITECTURE.md` | 贡献者→架构者 | 有第二个模块前 | 新人改了缓存层不知道有 edge/pages 两套路由 | `docs/03-architecture/` 5篇 + `contributing/turbopack/` | Google Ch.10：先讲目标/方案/权衡 |
| `CONTRIBUTING.md` | 外部贡献者→维护者 | 接受第一个外部 PR 前 | 收到 20 个格式 PR，review 累死 | `contributing.md` 薄索引 + 四目录；声明 trivial PR 关 | GitHub 社区规范 |
| `decisions/ADR-*.md` | 未来自己→现在自己 | 大改动写代码前 | 半年后没人记得为什么选 pnpm/turbo，只能重吵 | 隐含在设计文档评审流程里 | Google Ch.10：过评审再写码，归档为历史 |
| `docs/tutorial-*` | 新用户→维护者 | 发布前 | 用户跑不通 quickstart，直接弃用 | `01-getting-started/` | Diátaxis Tutorial |
| `docs/how-to-*` | 老用户→维护者 | 被问第二遍时 | 同一升级问题在 Discussions 答 50 遍 | `02-guides/upgrading/*` + `errors/*.mdx` | Diátaxis How-to |
| `docs/reference-*` | 开发者→维护者 | API 稳定时 | 靠读源码猜参数 | `03-api-reference/` 全 `.mdx` | Diátaxis Reference |
| `UPGRADING.md` | 老用户→维护者 | 第一次 breaking change | 升级骂声 + issue 爆炸 | 仓内 2 行存根，真文在 docs | Keep a Changelog 的 `Changed/Removed` 分组思想 |
| `CHANGELOG.md` | 用户/运维→维护者（工具生成） | 每次发版 | 靠翻 git log 找 breaking change | 用 GitHub Releases 代替文件（等价，L2 推荐留文件更通用） | https://keepachangelog.com/ + https://semver.org/ + Conventional Commits 三件套：`feat→MINOR, fix→PATCH, BREAKING→MAJOR` |
| `product/PRD-*.md` | 需求方→PM | 动工前 | 做了没人用的功能 | 对应 Discussions/RFC | — |
| `.github/*` | 贡献者→维护者 | L2 必配 | CI 被投毒、issue 无复现信息 | `ISSUE_TEMPLATE/ + pull_request_template.md + CODEOWNERS + workflows`（`.github/AGENTS.md` 要求 pin SHA） | GitHub 官方模板规范 |

## 4. 拿 next.js 当尺子：怎么量别的仓

1. 先看根：有 `AGENTS.md` 无 `CLAUDE.md`？有 `contributing.md` 是否薄？有 `CHANGELOG` 还是 Releases？
2. 再看 `docs/` 前缀排序 + 是否 `.mdx`（站点源码 vs 笔记）。
3. 再看 `.github/` + `errors/` 按码建档有没有。
4. 最后看 `skills/` 是单文件还是目录（判断 AI 成熟度）。

`skeleton/` 就是把这把尺子反过来：按 L2 最小闭环给你摆好，文件名英文照抄 next.js，注释中文告诉你每块抄什么。
