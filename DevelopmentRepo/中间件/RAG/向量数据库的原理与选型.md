<font style="color:rgb(26, 26, 26) !important;">上一篇我们把文本 chunk 变成了一组浮点数向量，还用 SiliconFlow 的 API 跑通了一个完整的向量化检索 demo。最后留了一个问题：向量生成之后存到哪里？</font>

<font style="color:rgb(26, 26, 26) !important;">当时的 demo 里，我们把所有向量放在一个 </font>`<font style="color:rgb(94, 129, 172);">List<float[]></font>`<font style="color:rgb(26, 26, 26) !important;"> 里，查询的时候遍历整个列表，逐个算余弦相似度，取最高的几个。demo 跑得很顺畅，因为只有几条数据。</font>

<font style="color:rgb(26, 26, 26) !important;">但你想想实际场景——一个电商平台的知识库，商品说明、退货政策、物流规则、促销活动、FAQ……分块之后轻轻松松几十万甚至上百万个 chunk，每个 chunk 对应一个 4096 维的向量。每次用户提问，你都要拿查询向量和这几十万个向量逐一比较？</font>

<font style="color:rgb(26, 26, 26) !important;">这显然不现实。</font>

<font style="color:rgb(26, 26, 26) !important;">这一篇，我们就来解决这个问题：向量存到哪里，怎么在海量向量中高效检索。</font>

## <font style="color:rgb(17, 24, 39);">向量存到哪里：为什么普通数据库不够用</font>
### <font style="color:rgb(17, 24, 39);">1. 最直觉的方案：用 MySQL 存向量</font>
<font style="color:rgb(26, 26, 26) !important;">既然向量就是一组浮点数，那最直觉的想法就是——存 MySQL 呗。</font>

<font style="color:rgb(26, 26, 26) !important;">方案很简单：在表里加一个 </font>`<font style="color:rgb(94, 129, 172);">TEXT</font>`<font style="color:rgb(26, 26, 26) !important;"> 或 </font>`<font style="color:rgb(94, 129, 172);">JSON</font>`<font style="color:rgb(26, 26, 26) !important;"> 字段，把向量序列化成字符串存进去。检索的时候把所有向量读出来，在应用层逐个计算余弦相似度，排序取 Top-K。</font>

```plain
CREATE TABLE chunk_vectors (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    chunk_text TEXT NOT NULL,
    vector JSON NOT NULL,          -- 存储 4096 维浮点数向量
    doc_id VARCHAR(64),
    category VARCHAR(32),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

<font style="color:rgb(26, 26, 26) !important;">能跑通吗？能。demo 阶段完全没问题。</font>

<font style="color:rgb(26, 26, 26) !important;">但这个方案有一个致命的问题——检索的时候，你必须把所有向量都读出来，在内存里逐个计算相似度。这就是所谓的暴力搜索（Brute-Force Search）。</font>

### <font style="color:rgb(17, 24, 39);">2. 暴力搜索的性能瓶颈</font>
<font style="color:rgb(26, 26, 26) !important;">咱们算一笔账。</font>

<font style="color:rgb(26, 26, 26) !important;">假设你的知识库有 100 万个 chunk，每个 chunk 的向量是 4096 维（用的 Qwen3-Embedding-8B 模型）。每次用户提问，系统需要：</font>

+ <font style="color:rgb(26, 26, 26) !important;">1.把用户的问题也向量化，得到一个 4096 维的查询向量</font>
+ <font style="color:rgb(26, 26, 26) !important;">2.从数据库里读出 100 万个向量</font>
+ <font style="color:rgb(26, 26, 26) !important;">3.逐个计算查询向量和这 100 万个向量的余弦相似度</font>
+ <font style="color:rgb(26, 26, 26) !important;">4.排序，取相似度最高的 Top-K 个</font>

<font style="color:rgb(26, 26, 26) !important;">第 3 步是瓶颈。每次余弦相似度计算需要做 4096 次乘法 + 4096 次加法 + 开方等运算。100 万个向量就是 100 万次这样的计算。</font>

<font style="color:rgb(26, 26, 26) !important;">具体要多久？在一台普通服务器上（单核 CPU），100 万个 4096 维向量的暴力搜索大约需要 2~5 秒。听起来好像还行？</font>

<font style="color:rgb(26, 26, 26) !important;">但别忘了：</font>

+ <font style="color:rgb(26, 26, 26) !important;">这只是单次查询的耗时，如果有 100 个用户同时提问呢？</font>
+ <font style="color:rgb(26, 26, 26) !important;">数据量还会增长，500 万、1000 万个 chunk 呢？</font>
+ <font style="color:rgb(26, 26, 26) !important;">实际的 RAG 系统对延迟很敏感，用户问一个问题不只是向量检索，还有很多其他步骤，体验很差</font>
+ <font style="color:rgb(26, 26, 26) !important;">而且每次查询都要把 100 万个向量从磁盘读到内存，I/O 开销也很大</font>

### <font style="color:rgb(17, 24, 39);">3. 近似最近邻搜索</font>
<font style="color:rgb(26, 26, 26) !important;">既然逐个比较太慢，能不能不比较所有向量，只比较其中一部分，就找到大概率最相似的那几个？</font>

<font style="color:rgb(26, 26, 26) !important;">答案是可以。这就是 </font>**<font style="color:rgb(17, 24, 39);">ANN</font>**<font style="color:rgb(26, 26, 26) !important;">（Approximate Nearest Neighbor，近似最近邻搜索）的核心思想。</font>

<font style="color:rgb(26, 26, 26) !important;">注意这里的关键词是“近似”——ANN 不保证找到的一定是全局最相似的向量，但它能在极短的时间内找到非常接近最优解的结果。</font>

<font style="color:rgb(26, 26, 26) !important;">打个比方：暴力搜索就像你要在一个 100 万人的城市里找和你最像的人，挨个去比对。ANN 则是先按区域划分，再按特征缩小范围，最后只在一小撮人里精确比较。你可能会错过某个住在偏远角落的“最佳匹配”，但你找到的人已经足够像了，而且速度快了几百倍。</font>

<font style="color:rgb(26, 26, 26) !important;">用数字来感受一下差距：</font>

| <font style="color:rgb(26, 26, 26) !important;">指标</font> | <font style="color:rgb(26, 26, 26) !important;">暴力搜索</font> | <font style="color:rgb(26, 26, 26) !important;">ANN 检索</font> |
| :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">100 万向量查询耗时</font> | <font style="color:rgb(26, 26, 26) !important;">2~5 秒</font> | <font style="color:rgb(26, 26, 26) !important;">1~10 毫秒</font> |
| <font style="color:rgb(26, 26, 26) !important;">召回率（Recall）</font> | <font style="color:rgb(26, 26, 26) !important;">100%（精确）</font> | <font style="color:rgb(26, 26, 26) !important;">95%~99%（近似）</font> |
| <font style="color:rgb(26, 26, 26) !important;">是否需要专门索引</font> | <font style="color:rgb(26, 26, 26) !important;">不需要</font> | <font style="color:rgb(26, 26, 26) !important;">需要</font> |
| <font style="color:rgb(26, 26, 26) !important;">适用数据量</font> | <font style="color:rgb(26, 26, 26) !important;">< 10 万</font> | <font style="color:rgb(26, 26, 26) !important;">百万~亿级</font> |


<font style="color:rgb(26, 26, 26) !important;">1~10 毫秒 vs 2~5 秒，速度差了几百到几千倍，而召回率只损失了 1%~5%。在实际的 RAG 场景中，这点精度损失几乎感知不到——你本来就是取 Top-K 个结果丢给大模型做参考，少了一个排名第 47 的 chunk 对最终回答没有影响。</font>

<font style="color:rgb(26, 26, 26) !important;">这就是向量数据库存在的核心理由：它不只是存向量，更重要的是提供高效的 ANN 检索能力。普通数据库能存向量，但做不了高效的 ANN 检索。</font>

<font style="color:rgb(17, 24, 39);">一句话概括：向量数据库 = 向量存储 + ANN 索引 + 高效检索。它是专门为“在海量向量中快速找到最相似的那几个”这件事而设计的。</font>

## <font style="color:rgb(17, 24, 39);">向量检索的核心算法：怎么不用逐个比较就能找到最相似的</font>
<font style="color:rgb(26, 26, 26) !important;">知道了 ANN 的目标——不逐个比较，快速找到近似最优解——接下来的问题是：具体怎么做到的？</font>

<font style="color:rgb(26, 26, 26) !important;">这一节我们讲两种最主流的 ANN 索引算法：IVF 和 HNSW。不涉及数学推导，重点是让你理解它们的核心思想和工程上的取舍。</font>

### <font style="color:rgb(17, 24, 39);">1. 类比：在一本 10 万页的字典里查一个词</font>
<font style="color:rgb(26, 26, 26) !important;">在讲具体算法之前，先想一个生活中的场景。</font>

<font style="color:rgb(26, 26, 26) !important;">你手上有一本 10 万页的字典，要查 </font>`<font style="color:rgb(94, 129, 172);">serendipity</font>`<font style="color:rgb(26, 26, 26) !important;"> 这个词。你会怎么做？</font>

<font style="color:rgb(26, 26, 26) !important;">肯定不会从第 1 页翻到第 100000 页。你会：</font>

+ <font style="color:rgb(26, 26, 26) !important;">1.先看目录，确定 S 开头的词在哪个范围</font>
+ <font style="color:rgb(26, 26, 26) !important;">2.翻到大概的位置，再根据前几个字母缩小范围</font>
+ <font style="color:rgb(26, 26, 26) !important;">3.最后在一小段页面里精确查找</font>

<font style="color:rgb(26, 26, 26) !important;">这个过程的本质是：通过某种结构（目录、索引），把搜索范围从“全部”缩小到“一小部分”，然后在小范围内精确查找。</font>

<font style="color:rgb(26, 26, 26) !important;">向量索引的思路完全一样——只不过字典里的“词”变成了“向量”，字母顺序变成了空间位置。</font>

### <font style="color:rgb(17, 24, 39);">2. IVF（倒排文件索引）：先分区再搜索</font>
<font style="color:rgb(26, 26, 26) !important;">IVF 的全称是 Inverted File Index（倒排文件索引）。名字听起来很学术，但思路非常直觉。</font>

#### <font style="color:rgb(17, 24, 39);">2.1 IVF 的工作原理</font>
<font style="color:rgb(26, 26, 26) !important;">IVF 的核心思想就一句话：把向量空间划分成若干个区域，查询时只在最可能的几个区域里搜索。</font>

<font style="color:rgb(26, 26, 26) !important;">具体怎么做？分两个阶段：</font>

<font style="color:rgb(26, 26, 26) !important;">建索引阶段（离线）：</font>

+ <font style="color:rgb(26, 26, 26) !important;">1.用聚类算法（通常是 K-Means）把所有向量分成 </font>`<font style="color:rgb(94, 129, 172);">nlist</font>`<font style="color:rgb(26, 26, 26) !important;"> 个簇（cluster）</font>
+ <font style="color:rgb(26, 26, 26) !important;">2.每个簇有一个中心点（centroid），代表这个簇里所有向量的"平均位置"</font>
+ <font style="color:rgb(26, 26, 26) !important;">3.每个向量被分配到离它最近的那个簇</font>

<font style="color:rgb(26, 26, 26) !important;">检索阶段（在线）：</font>

+ <font style="color:rgb(26, 26, 26) !important;">1.拿到查询向量后，先计算它和所有簇中心点的距离</font>
+ <font style="color:rgb(26, 26, 26) !important;">2.找到最近的 </font>`<font style="color:rgb(94, 129, 172);">nprobe</font>`<font style="color:rgb(26, 26, 26) !important;"> 个簇（nprobe 是一个可调参数）</font>
+ <font style="color:rgb(26, 26, 26) !important;">3.只在这 </font>`<font style="color:rgb(94, 129, 172);">nprobe</font>`<font style="color:rgb(26, 26, 26) !important;"> 个簇里的向量中做精确搜索</font>

<font style="color:rgb(26, 26, 26) !important;">打个比方：你要在一个大型图书馆里找一本关于“Java 并发编程”的书。IVF 的做法是——先看楼层指引，确定计算机类在 3 楼，编程语言在 3 楼 A 区，然后只在 3 楼 A 区的书架上找。你不需要把整个图书馆的书都翻一遍。</font>

<font style="color:rgb(26, 26, 26) !important;">假设 </font>`<font style="color:rgb(94, 129, 172);">nlist = 100</font>`<font style="color:rgb(26, 26, 26) !important;">（分成 100 个簇），</font>`<font style="color:rgb(94, 129, 172);">nprobe = 10</font>`<font style="color:rgb(26, 26, 26) !important;">（查询时搜索 10 个簇），那么每次查询只需要搜索大约 10% 的向量，速度提升约 10 倍。</font>

#### <font style="color:rgb(17, 24, 39);">2.2 IVF 的优缺点</font>
| <font style="color:rgb(26, 26, 26) !important;">优点</font> | <font style="color:rgb(26, 26, 26) !important;">缺点</font> |
| :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">原理简单，容易理解和调优</font> | <font style="color:rgb(26, 26, 26) !important;">需要训练聚类模型（数据量大时训练较慢）</font> |
| <font style="color:rgb(26, 26, 26) !important;">内存占用相对较低</font> | <font style="color:rgb(26, 26, 26) !important;">聚类边界处的向量可能被漏掉（影响召回率）</font> |
| <font style="color:rgb(26, 26, 26) !important;">适合数据量非常大的场景</font> | <font style="color:rgb(26, 26, 26) !important;">nlist 和 nprobe 的调参需要经验</font> |
| <font style="color:rgb(26, 26, 26) !important;">支持增量插入（但可能需要定期重新聚类）</font> | <font style="color:rgb(26, 26, 26) !important;">数据分布不均匀时效果下降</font> |


<font style="color:rgb(17, 24, 39);">IVF 还有几个变体：IVF_FLAT 是在簇内做精确搜索，IVF_SQ8 是对簇内向量做量化压缩以节省内存，IVF_PQ 则用乘积量化进一步压缩。后面的选型表格里会对比它们的差异。</font>

### <font style="color:rgb(17, 24, 39);">3. HNSW（分层可导航小世界图）：最主流的索引算法</font>
<font style="color:rgb(26, 26, 26) !important;">HNSW 的全称是 Hierarchical Navigable Small World Graph（分层可导航小世界图）。名字很长，但它是目前最主流、效果最好的 ANN 索引算法，几乎所有向量数据库都把它作为默认或推荐的索引类型。</font>

#### <font style="color:rgb(17, 24, 39);">3.1 HNSW 的核心思想：多层图结构</font>
<font style="color:rgb(26, 26, 26) !important;">要理解 HNSW，先从一个生活场景开始。</font>

<font style="color:rgb(26, 26, 26) !important;">假设你要找一个"住在北京朝阳区、会写 Java、喜欢打篮球"的人，但你手上没有任何名单，只能通过社交关系去找。你会怎么做？</font>

<font style="color:rgb(26, 26, 26) !important;">你不会挨个问全中国 14 亿人。你会这样：</font>

+ <font style="color:rgb(26, 26, 26) !important;">1.先在你认识的人里找——“谁在北京？”——你的朋友老王在北京</font>
+ <font style="color:rgb(26, 26, 26) !important;">2.问老王——“你认识朝阳区的人吗？”——老王介绍了他同事小李</font>
+ <font style="color:rgb(26, 26, 26) !important;">3.问小李——“你认识会写 Java 的人吗？”——小李介绍了他的大学同学张三</font>
+ <font style="color:rgb(26, 26, 26) !important;">4.张三恰好也喜欢打篮球——找到了！</font>

<font style="color:rgb(26, 26, 26) !important;">每一步你都在靠近目标，而且每一步只需要问几个人，不需要遍历所有人。</font>

<font style="color:rgb(26, 26, 26) !important;">HNSW 的思路和这个完全一样，只不过把“人”换成了“向量”，把“社交关系”换成了“图中的边”。</font>

<font style="color:rgb(26, 26, 26) !important;">HNSW 的核心结构是一个多层图：</font>

+ <font style="color:rgb(26, 26, 26) !important;">最底层（Layer 0）包含所有向量，每个向量和它附近的若干个向量相连</font>
+ <font style="color:rgb(26, 26, 26) !important;">往上每一层的向量数量越来越少（随机抽取），但连接的跨度越来越大</font>
+ <font style="color:rgb(26, 26, 26) !important;">最顶层只有很少的几个向量，但它们之间的连接覆盖了整个向量空间</font>

<font style="color:rgb(26, 26, 26) !important;">检索的时候，从最顶层开始，快速定位到目标的大致区域，然后逐层下降，每一层都在更精细的范围内搜索，最终在最底层找到最相似的向量。</font>

#### <font style="color:rgb(17, 24, 39);">3.2 用一个具体例子走一遍 HNSW 的检索过程</font>
<font style="color:rgb(26, 26, 26) !important;">为了让你更直观地理解，咱们用一个简化的例子走一遍。</font>

<font style="color:rgb(26, 26, 26) !important;">假设向量数据库里有 8 个向量（A、B、C、D、E、F、G、H），HNSW 建了 3 层图。现在要查询和向量 Q 最相似的向量。</font>

<font style="color:rgb(26, 26, 26) !important;">Layer 2（顶层）：只有 A 和 E 两个向量</font>

+ <font style="color:rgb(26, 26, 26) !important;">从 A 开始，计算 Q 和 A 的距离、Q 和 E 的距离</font>
+ <font style="color:rgb(26, 26, 26) !important;">发现 E 离 Q 更近，移动到 E</font>

<font style="color:rgb(26, 26, 26) !important;">Layer 1（中间层）：有 A、C、E、G 四个向量</font>

+ <font style="color:rgb(26, 26, 26) !important;">从 E 出发，看 E 的邻居：C 和 G</font>
+ <font style="color:rgb(26, 26, 26) !important;">计算 Q 和 C、Q 和 G 的距离</font>
+ <font style="color:rgb(26, 26, 26) !important;">发现 G 离 Q 更近，移动到 G</font>

<font style="color:rgb(26, 26, 26) !important;">Layer 0（底层）：所有 8 个向量都在</font>

+ <font style="color:rgb(26, 26, 26) !important;">从 G 出发，看 G 的邻居：F 和 H</font>
+ <font style="color:rgb(26, 26, 26) !important;">计算 Q 和 F、Q 和 H 的距离</font>
+ <font style="color:rgb(26, 26, 26) !important;">发现 H 离 Q 最近</font>
+ <font style="color:rgb(26, 26, 26) !important;">再看 H 的邻居，没有比 H 更近的了</font>
+ <font style="color:rgb(26, 26, 26) !important;">结果：H 是和 Q 最相似的向量</font>

<font style="color:rgb(26, 26, 26) !important;">整个过程只计算了 6 次距离（A、E、C、G、F、H），而不是 8 次。数据量小的时候差距不明显，但如果有 100 万个向量，HNSW 通常只需要计算几百到几千次距离就能找到结果。</font>

#### <font style="color:rgb(17, 24, 39);">3.3 为什么 HNSW 这么快</font>
<font style="color:rgb(26, 26, 26) !important;">HNSW 快的原因可以归结为两点：</font>

<font style="color:rgb(26, 26, 26) !important;">第一，多层结构实现了“粗到细”的搜索。顶层的少量向量帮你快速跳到目标附近，底层的密集连接帮你精确定位。这和跳表（Skip List）的思想很像——如果你了解 Redis 的有序集合（ZSet），它底层用的就是跳表，原理是相通的。</font>

<font style="color:rgb(26, 26, 26) !important;">第二，“小世界”特性保证了图的连通性。在 HNSW 的图中，任意两个向量之间只需要经过很少的“跳转”就能到达（类似“六度分隔理论”——你和世界上任何一个人之间最多只隔 6 个人）。这意味着搜索不会陷入死角，总能快速逼近目标。</font>

#### <font style="color:rgb(17, 24, 39);">3.4 HNSW 的代价：内存占用</font>
<font style="color:rgb(26, 26, 26) !important;">HNSW 的检索速度和精度都很优秀，但它有一个明显的代价：内存占用大。</font>

<font style="color:rgb(26, 26, 26) !important;">因为 HNSW 需要在内存中维护整个图结构——不仅要存所有向量本身，还要存向量之间的连接关系（边）。每个向量在每一层都有若干条边，这些边的存储开销不小。</font>

<font style="color:rgb(26, 26, 26) !important;">具体来说，HNSW 有两个关键参数影响内存和性能：</font>

| <font style="color:rgb(26, 26, 26) !important;">参数</font> | <font style="color:rgb(26, 26, 26) !important;">含义</font> | <font style="color:rgb(26, 26, 26) !important;">调大的效果</font> | <font style="color:rgb(26, 26, 26) !important;">调小的效果</font> |
| :--- | :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">M</font> | <font style="color:rgb(26, 26, 26) !important;">每个向量在每层的最大连接数</font> | <font style="color:rgb(26, 26, 26) !important;">召回率更高，但内存占用更大，建索引更慢</font> | <font style="color:rgb(26, 26, 26) !important;">内存省，但召回率可能下降</font> |
| <font style="color:rgb(26, 26, 26) !important;">efConstruction</font> | <font style="color:rgb(26, 26, 26) !important;">建索引时的搜索宽度</font> | <font style="color:rgb(26, 26, 26) !important;">索引质量更高（连接更合理），但建索引更慢</font> | <font style="color:rgb(26, 26, 26) !important;">建索引快，但索引质量可能下降</font> |


<font style="color:rgb(26, 26, 26) !important;">检索时还有一个参数 </font>`<font style="color:rgb(94, 129, 172);">ef</font>`<font style="color:rgb(26, 26, 26) !important;">（搜索宽度），控制检索时探索的候选集大小。</font>`<font style="color:rgb(94, 129, 172);">ef</font>`<font style="color:rgb(26, 26, 26) !important;"> 越大，召回率越高，但检索越慢。</font>

<font style="color:rgb(17, 24, 39);">一个粗略的估算：100 万个 4096 维向量，用 HNSW 索引（M=16），大约需要 16~20 GB 内存。如果你的服务器内存有限，可能需要考虑 IVF 系列索引，它们的内存占用要小得多。</font>

### <font style="color:rgb(17, 24, 39);">4. 索引算法对比：怎么选</font>
<font style="color:rgb(26, 26, 26) !important;">Milvus 支持多种索引类型，下面是最常用的几种对比：</font>

| <font style="color:rgb(26, 26, 26) !important;">索引类型</font> | <font style="color:rgb(26, 26, 26) !important;">核心思想</font> | <font style="color:rgb(26, 26, 26) !important;">检索速度</font> | <font style="color:rgb(26, 26, 26) !important;">召回率</font> | <font style="color:rgb(26, 26, 26) !important;">内存占用</font> | <font style="color:rgb(26, 26, 26) !important;">适用数据量</font> | <font style="color:rgb(26, 26, 26) !important;">适用场景</font> |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">FLAT</font> | <font style="color:rgb(26, 26, 26) !important;">暴力搜索，不建索引</font> | <font style="color:rgb(26, 26, 26) !important;">最慢</font> | <font style="color:rgb(26, 26, 26) !important;">100%（精确）</font> | <font style="color:rgb(26, 26, 26) !important;">低（只存原始向量）</font> | <font style="color:rgb(26, 26, 26) !important;">< 10 万</font> | <font style="color:rgb(26, 26, 26) !important;">对精度要求极高，数据量小</font> |
| <font style="color:rgb(26, 26, 26) !important;">IVF_FLAT</font> | <font style="color:rgb(26, 26, 26) !important;">聚类分区 + 簇内精确搜索</font> | <font style="color:rgb(26, 26, 26) !important;">快</font> | <font style="color:rgb(26, 26, 26) !important;">95%~99%</font> | <font style="color:rgb(26, 26, 26) !important;">较低</font> | <font style="color:rgb(26, 26, 26) !important;">百万~千万</font> | <font style="color:rgb(26, 26, 26) !important;">数据量大，内存有限</font> |
| <font style="color:rgb(26, 26, 26) !important;">IVF_SQ8</font> | <font style="color:rgb(26, 26, 26) !important;">聚类分区 + 标量量化压缩</font> | <font style="color:rgb(26, 26, 26) !important;">快</font> | <font style="color:rgb(26, 26, 26) !important;">93%~97%</font> | <font style="color:rgb(26, 26, 26) !important;">低（向量压缩为 1/4）</font> | <font style="color:rgb(26, 26, 26) !important;">千万~亿级</font> | <font style="color:rgb(26, 26, 26) !important;">数据量很大，愿意牺牲一点精度换内存</font> |
| <font style="color:rgb(26, 26, 26) !important;">HNSW</font> | <font style="color:rgb(26, 26, 26) !important;">多层图结构</font> | <font style="color:rgb(26, 26, 26) !important;">最快</font> | <font style="color:rgb(26, 26, 26) !important;">97%~99.5%</font> | <font style="color:rgb(26, 26, 26) !important;">高（需存图结构）</font> | <font style="color:rgb(26, 26, 26) !important;">百万~千万</font> | <font style="color:rgb(26, 26, 26) !important;">对速度和精度都有要求，内存充足</font> |
| <font style="color:rgb(26, 26, 26) !important;">DISKANN</font> | <font style="color:rgb(26, 26, 26) !important;">基于磁盘的图索引</font> | <font style="color:rgb(26, 26, 26) !important;">较快</font> | <font style="color:rgb(26, 26, 26) !important;">95%~98%</font> | <font style="color:rgb(26, 26, 26) !important;">低（索引在磁盘）</font> | <font style="color:rgb(26, 26, 26) !important;">亿级</font> | <font style="color:rgb(26, 26, 26) !important;">数据量极大，内存不够放 HNSW</font> |


<font style="color:rgb(26, 26, 26) !important;">怎么选？一个简单的决策路径：</font>

+ <font style="color:rgb(26, 26, 26) !important;">数据量 < 10 万，直接用 FLAT，暴力搜索就够了</font>
+ <font style="color:rgb(26, 26, 26) !important;">数据量 10 万~500 万，内存充足 → HNSW；内存有限 → IVF_FLAT</font>
+ <font style="color:rgb(26, 26, 26) !important;">数据量 500 万~5000 万，HNSW 如果内存放得下就用 HNSW，放不下用 IVF_SQ8</font>
+ <font style="color:rgb(26, 26, 26) !important;">数据量 > 5000 万，考虑 DISKANN 或 IVF_PQ</font>

<font style="color:rgb(26, 26, 26) !important;">对于大多数 RAG 项目来说，数据量在百万级别，HNSW 是最优选择。这也是为什么后面的实战代码里我们用 HNSW 作为索引类型。</font>

## <font style="color:rgb(17, 24, 39);">主流向量数据库对比与选型</font>
<font style="color:rgb(26, 26, 26) !important;">理解了向量检索的算法原理之后，下一个问题是：用哪个向量数据库？</font>

<font style="color:rgb(26, 26, 26) !important;">市面上的向量数据库方案大致分为两类。</font>

### <font style="color:rgb(17, 24, 39);">1. 向量数据库的分类</font>
#### <font style="color:rgb(17, 24, 39);">1.1 专用向量数据库</font>
<font style="color:rgb(26, 26, 26) !important;">从零开始为向量检索设计的数据库，向量是一等公民。代表产品：Milvus、Qdrant、Weaviate、Pinecone、Chroma。</font>

<font style="color:rgb(26, 26, 26) !important;">它们的特点是：原生支持多种 ANN 索引算法，针对向量检索做了大量底层优化（内存管理、并行计算、索引构建等），通常还支持标量过滤（在向量检索的同时按元数据条件过滤）。</font>

#### <font style="color:rgb(17, 24, 39);">1.2 传统数据库的向量扩展</font>
<font style="color:rgb(26, 26, 26) !important;">在已有的关系型数据库上加一个向量检索插件。代表产品：pgvector（PostgreSQL 的扩展）、MySQL 8.0+ 的向量支持、Elasticsearch 的 kNN 搜索。</font>

<font style="color:rgb(26, 26, 26) !important;">它们的优势是不用引入新的基础设施——如果你的项目已经在用 PostgreSQL，加一个 pgvector 扩展就能存向量、做检索，运维成本低。但在大数据量下的检索性能、索引类型的丰富度、以及向量检索的专项优化上，和专用向量数据库还是有差距。</font>

#### <font style="color:rgb(17, 24, 39);">1.3 怎么选</font>
<font style="color:rgb(26, 26, 26) !important;">一个简单的判断标准：</font>

+ <font style="color:rgb(26, 26, 26) !important;">如果你的向量数据量 < 50 万，且项目已经在用 PostgreSQL → pgvector 够用，省事</font>
+ <font style="color:rgb(26, 26, 26) !important;">如果向量数据量 > 50 万，或者对检索性能有较高要求 → 用专用向量数据库</font>
+ <font style="color:rgb(26, 26, 26) !important;">如果是学习和原型验证阶段 → Chroma（轻量，Python 生态好）或 Milvus（功能全，Java SDK 完善）</font>

### <font style="color:rgb(17, 24, 39);">3. 为什么选 Milvus</font>

+ <font style="color:rgb(26, 26, 26) !important;">开源且社区活跃：Apache 2.0 协议，截止 26.2.20 号 GitHub 上 42.8k+ star，文档和社区资源丰富</font>
+ <font style="color:rgb(26, 26, 26) !important;">Java SDK 完善：本系列的代码示例用 Java，Milvus 的 Java SDK（</font>`<font style="color:rgb(94, 129, 172);">io.milvus:milvus-sdk-java</font>`<font style="color:rgb(26, 26, 26) !important;">）功能完整，API 设计清晰</font>
+ <font style="color:rgb(26, 26, 26) !important;">支持大规模数据：从几万到几十亿向量都能应对，单机模式适合开发和中小规模，集群模式适合大规模生产</font>

+ <font style="color:rgb(26, 26, 26) !important;">标量过滤能力强：支持在向量检索的同时按元数据字段过滤（比如：只在退货政策类的 chunk 里检索），这在 RAG 场景中非常实用</font>

## <font style="color:rgb(17, 24, 39);">Milvus 核心概念：和传统数据库做类比</font>
<font style="color:rgb(26, 26, 26) !important;">在动手写代码之前，先搞清楚 Milvus 里的几个核心概念。如果你用过 MySQL，理解起来会很快——Milvus 的概念体系和关系型数据库有很多对应关系。</font>

### <font style="color:rgb(17, 24, 39);">1. Collection = 表</font>
<font style="color:rgb(26, 26, 26) !important;">Collection 是 Milvus 中数据组织的基本单位，对应 MySQL 中的表（Table）。</font>

<font style="color:rgb(26, 26, 26) !important;">一个 Collection 存储一类向量数据。比如在我们的电商客服知识库场景中，可以创建一个名为 </font>`<font style="color:rgb(94, 129, 172);">customer_service_chunks</font>`<font style="color:rgb(26, 26, 26) !important;"> 的 Collection，里面存所有客服知识库的 chunk 向量。</font>

<font style="color:rgb(26, 26, 26) !important;">如果你有多个业务场景（比如客服知识库、商品搜索、内容推荐），通常建议为每个场景创建一个独立的 Collection。</font>

### <font style="color:rgb(17, 24, 39);">2. Schema = 表结构</font>
<font style="color:rgb(26, 26, 26) !important;">Schema 定义了 Collection 中每条数据包含哪些字段，对应 MySQL 中的表结构（CREATE TABLE 时定义的列）。</font>

<font style="color:rgb(26, 26, 26) !important;">一个典型的 RAG 场景的 Schema 包含三类字段：</font>

| <font style="color:rgb(26, 26, 26) !important;">字段类型</font> | <font style="color:rgb(26, 26, 26) !important;">示例</font> | <font style="color:rgb(26, 26, 26) !important;">说明</font> |
| :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">主键字段</font> | <font style="color:rgb(26, 26, 26) !important;">id（Int64 或 VarChar）</font> | <font style="color:rgb(26, 26, 26) !important;">每条数据的唯一标识，类似 MySQL 的主键</font> |
| <font style="color:rgb(26, 26, 26) !important;">向量字段</font> | <font style="color:rgb(26, 26, 26) !important;">vector（FloatVector）</font> | <font style="color:rgb(26, 26, 26) !important;">存储 Embedding 向量，需要指定维度</font> |
| <font style="color:rgb(26, 26, 26) !important;">标量字段</font> | <font style="color:rgb(26, 26, 26) !important;">chunk_text、doc_id、category 等</font> | <font style="color:rgb(26, 26, 26) !important;">存储元数据，用于过滤和展示</font> |


#### <font style="color:rgb(17, 24, 39);">2.1 向量字段和标量字段的区别</font>
<font style="color:rgb(26, 26, 26) !important;">这里要特别说明一下向量字段和标量字段的区别，因为这是 Milvus 和传统数据库最大的不同。</font>

<font style="color:rgb(26, 26, 26) !important;">标量字段存储的是普通数据（字符串、数字、布尔值等），和 MySQL 的列没什么区别。你可以对标量字段建索引、做等值查询、范围查询、模糊匹配等。</font>

<font style="color:rgb(26, 26, 26) !important;">向量字段存储的是高维浮点数数组（比如 4096 维的 float 数组），它不能做等值查询（两个向量完全相等的概率几乎为零），只能做相似度检索（找最近的 Top-K 个）。向量字段需要建专门的向量索引（HNSW、IVF 等），这和标量字段的 B+ 树索引是完全不同的东西。</font>

### <font style="color:rgb(17, 24, 39);">3. Index = 索引</font>
<font style="color:rgb(26, 26, 26) !important;">Milvus 中的索引分两种：</font>

+ <font style="color:rgb(26, 26, 26) !important;">向量索引：为向量字段创建的 ANN 索引（HNSW、IVF_FLAT 等），用于加速向量相似度检索。这是 Milvus 的核心能力。</font>
+ <font style="color:rgb(26, 26, 26) !important;">标量索引：为标量字段创建的索引，用于加速过滤条件的执行。类似 MySQL 的 B+ 树索引。</font>

<font style="color:rgb(26, 26, 26) !important;">在 RAG 场景中，通常需要同时用到两种索引：向量索引用于找到语义最相似的 chunk，标量索引用于按元数据过滤（比如只搜索某个类别的 chunk）。</font>

### <font style="color:rgb(17, 24, 39);">4. Partition = 分区</font>
<font style="color:rgb(26, 26, 26) !important;">Partition 是 Collection 内部的数据分区，对应 MySQL 的分区表。</font>

<font style="color:rgb(26, 26, 26) !important;">你可以按某个业务维度把数据分到不同的 Partition 里。比如按文档类别分区：退货政策放一个 Partition，物流规则放一个 Partition，促销活动放一个 Partition。</font>

<font style="color:rgb(26, 26, 26) !important;">检索的时候可以指定只在某个 Partition 里搜索，这样搜索范围更小，速度更快。</font>

<font style="color:rgb(26, 26, 26) !important;">不过需要注意：Partition 不是必须的。如果你的数据量不大（< 100 万），或者没有明确的分区维度，不分区也完全没问题。用标量过滤（在 WHERE 条件里加 </font>`<font style="color:rgb(94, 129, 172);">category = 'return_policy'</font>`<font style="color:rgb(26, 26, 26) !important;">）也能达到类似的效果，只是在数据量很大时性能不如 Partition。</font>

### <font style="color:rgb(17, 24, 39);">3. 创建 Collection 和 Schema</font>
<font style="color:rgb(17, 24, 39);">下述的示例代码，都放在了 </font>[<font style="color:rgb(17, 24, 39);">TinyRAG</font>](https://github.com/nageoffer/tinyrag)<font style="color:rgb(17, 24, 39);"> 项目的 com.nageoffer.ai.tinyrag.milvus 包下，可自行测试。</font>

<font style="color:rgb(26, 26, 26) !important;">先连接 Milvus，然后创建一个用于存储电商客服知识库 chunk 的 Collection。</font>

```plain
import io.milvus.v2.client.ConnectConfig;
import io.milvus.v2.client.MilvusClientV2;
import io.milvus.v2.common.DataType;
import io.milvus.v2.service.collection.request.AddFieldReq;
import io.milvus.v2.service.collection.request.CreateCollectionReq;

public class MilvusDemo {

    // 向量维度，和 Embedding 模型保持一致（Qwen3-Embedding-8B 输出 4096 维）
    private static final int VECTOR_DIM = 4096;
    private static final String COLLECTION_NAME = "customer_service_chunks";

    public static void main(String[] args) {
        // 1. 连接 Milvus
        ConnectConfig connectConfig = ConnectConfig.builder()
                .uri("http://localhost:19530")
                .build();
        MilvusClientV2 client = new MilvusClientV2(connectConfig);
        System.out.println("已连接到 Milvus");

        // 2. 定义 Schema
        CreateCollectionReq.CollectionSchema schema = client.createSchema();

        // 主键字段：自增 ID
        schema.addField(AddFieldReq.builder()
                .fieldName("id")
                .dataType(DataType.Int64)
                .isPrimaryKey(true)
                .autoID(true)
                .build());

        // 向量字段：存储 Embedding 向量
        schema.addField(AddFieldReq.builder()
                .fieldName("vector")
                .dataType(DataType.FloatVector)
                .dimension(VECTOR_DIM)
                .build());

        // 标量字段：chunk 原文
        schema.addField(AddFieldReq.builder()
                .fieldName("chunk_text")
                .dataType(DataType.VarChar)
                .maxLength(8192)
                .build());

        // 标量字段：文档 ID（标识这个 chunk 来自哪个文档）
        schema.addField(AddFieldReq.builder()
                .fieldName("doc_id")
                .dataType(DataType.VarChar)
                .maxLength(64)
                .build());

        // 标量字段：分类（退货政策、物流规则、促销活动等）
        schema.addField(AddFieldReq.builder()
                .fieldName("category")
                .dataType(DataType.VarChar)
                .maxLength(32)
                .build());

        // 3. 创建 Collection
        CreateCollectionReq createCollectionReq = CreateCollectionReq.builder()
                .collectionName(COLLECTION_NAME)
                .collectionSchema(schema)
                .build();
        client.createCollection(createCollectionReq);
        System.out.println("Collection 创建成功：" + COLLECTION_NAME);
    }
}
```

<font style="color:rgb(26, 26, 26) !important;">几个要点说明：</font>

+ `<font style="color:rgb(94, 129, 172);">FloatVector</font>`<font style="color:rgb(26, 26, 26) !important;"> 的 </font>`<font style="color:rgb(94, 129, 172);">dimension</font>`<font style="color:rgb(26, 26, 26) !important;"> 必须和你用的 Embedding 模型输出维度一致。我们用的 Qwen3-Embedding-8B 输出 4096 维，这里就填 4096</font>
+ `<font style="color:rgb(94, 129, 172);">VarChar</font>`<font style="color:rgb(26, 26, 26) !important;"> 类型需要指定 </font>`<font style="color:rgb(94, 129, 172);">maxLength</font>`<font style="color:rgb(26, 26, 26) !important;">，这是 Milvus 的要求。</font>`<font style="color:rgb(94, 129, 172);">chunk_text</font>`<font style="color:rgb(26, 26, 26) !important;"> 设成 8192 足够存一个 chunk 的原文</font>
+ `<font style="color:rgb(94, 129, 172);">autoID(true)</font>`<font style="color:rgb(26, 26, 26) !important;"> 表示主键由 Milvus 自动生成，插入数据时不需要手动指定 ID</font>
+ <font style="color:rgb(26, 26, 26) !important;">这里没有在创建 Collection 时同时创建索引，后面会单独创建——这样更清晰，也方便你理解每一步在做什么</font>

<font style="color:rgb(26, 26, 26) !important;">在 Attu 管理界面中可以看到刚创建的 Collection 和它的 Schema。</font>

### <font style="color:rgb(17, 24, 39);">4. 插入向量数据</font>
<font style="color:rgb(26, 26, 26) !important;">Collection 创建好了，接下来往里面插入数据。在实际的 RAG 系统中，数据来源是这样的：原始文档 → Tika 提取文本 → 分块 → 向量化 → 插入 Milvus。这里我们直接模拟几条电商客服知识库的 chunk 数据。</font>

<font style="color:rgb(26, 26, 26) !important;">为了让 demo 完整可运行，我们复用上一篇的 SiliconFlow Embedding API 来生成真实的向量，而不是用随机数。</font>

```plain
import com.google.gson.Gson;
import com.google.gson.JsonArray;
import com.google.gson.JsonObject;
import io.milvus.v2.service.vector.request.InsertReq;
import io.milvus.v2.service.vector.response.InsertResp;
import okhttp3.*;

import java.io.IOException;
import java.util.*;

public class MilvusInsertDemo {

    private static final String SILICONFLOW_API_KEY = "你的 SiliconFlow API Key";
    private static final String EMBEDDING_URL = "https://api.siliconflow.cn/v1/embeddings";
    private static final String EMBEDDING_MODEL = "Qwen/Qwen3-Embedding-8B";
    private static final Gson GSON = new Gson();
    private static final OkHttpClient HTTP_CLIENT = new OkHttpClient();

    public static void main(String[] args) throws IOException {
        // 连接 Milvus（省略，同上一节）
        MilvusClientV2 client = connectMilvus();

        // 模拟电商客服知识库的 chunk 数据
        List<String> chunkTexts = List.of(
                "退货政策：自签收之日起 7 天内，商品未拆封、不影响二次销售的情况下，支持无理由退货。退货运费由买家承担，质量问题除外。",
                "退货政策：生鲜食品、定制商品、贴身衣物等特殊商品不支持无理由退货。如有质量问题，请在签收后 48 小时内联系客服并提供照片凭证。",
                "物流规则：普通商品下单后 48 小时内发货，预售商品以商品详情页标注的发货时间为准。偏远地区（新疆、西藏、青海等）可能需要额外 2~3 天。",
                "物流规则：支持顺丰、中通、圆通、韵达等主流快递。默认使用中通快递，如需指定快递公司，请在下单时备注，可能产生额外运费。",
                "促销活动：2026 年春节大促，全场满 300 减 50，满 500 减 100。活动时间：2026 年 1 月 20 日至 2 月 5 日。优惠券不可叠加使用。"
        );
        List<String> docIds = List.of("doc_return_001", "doc_return_001", "doc_logistics_001", "doc_logistics_001", "doc_promo_001");
        List<String> categories = List.of("return_policy", "return_policy", "logistics", "logistics", "promotion");

        // 调用 Embedding API 生成向量
        List<List<Float>> vectors = getEmbeddings(chunkTexts);

        // 组装插入数据
        List<JsonObject> rows = new ArrayList<>();
        for (int i = 0; i < chunkTexts.size(); i++) {
            JsonObject row = new JsonObject();
            row.addProperty("chunk_text", chunkTexts.get(i));
            row.addProperty("doc_id", docIds.get(i));
            row.addProperty("category", categories.get(i));
            row.add("vector", GSON.toJsonTree(vectors.get(i)));
            rows.add(row);
        }

        // 插入 Milvus
        InsertReq insertReq = InsertReq.builder()
                .collectionName("customer_service_chunks")
                .data(rows)
                .build();
        InsertResp insertResp = client.insert(insertReq);
        System.out.println("插入成功，数量：" + insertResp.getInsertCnt());
    }

    /**
     * 调用 SiliconFlow Embedding API，批量生成向量
     */
    private static List<List<Float>> getEmbeddings(List<String> texts) throws IOException {
        JsonObject requestBody = new JsonObject();
        requestBody.addProperty("model", EMBEDDING_MODEL);
        requestBody.add("input", GSON.toJsonTree(texts));

        Request request = new Request.Builder()
                .url(EMBEDDING_URL)
                .addHeader("Authorization", "Bearer " + SILICONFLOW_API_KEY)
                .addHeader("Content-Type", "application/json")
                .post(RequestBody.create(GSON.toJson(requestBody),
                        MediaType.parse("application/json")))
                .build();

        try (Response response = HTTP_CLIENT.newCall(request).execute()) {
            String body = response.body().string();
            JsonObject json = GSON.fromJson(body, JsonObject.class);
            JsonArray dataArray = json.getAsJsonArray("data");

            List<List<Float>> vectors = new ArrayList<>();
            for (int i = 0; i < dataArray.size(); i++) {
                JsonArray embeddingArray = dataArray.get(i).getAsJsonObject()
                        .getAsJsonArray("embedding");
                List<Float> vector = new ArrayList<>();
                for (int j = 0; j < embeddingArray.size(); j++) {
                    vector.add(embeddingArray.get(j).getAsFloat());
                }
                vectors.add(vector);
            }
            return vectors;
        }
    }
}
```

<font style="color:rgb(26, 26, 26) !important;">插入数据时有几个细节值得注意：</font>

+ <font style="color:rgb(26, 26, 26) !important;">Milvus v2 API 使用 </font>`<font style="color:rgb(94, 129, 172);">JsonObject</font>`<font style="color:rgb(26, 26, 26) !important;"> 的 List 作为插入数据的格式，每个 </font>`<font style="color:rgb(94, 129, 172);">JsonObject</font>`<font style="color:rgb(26, 26, 26) !important;"> 代表一行数据</font>
+ <font style="color:rgb(26, 26, 26) !important;">因为我们设置了 </font>`<font style="color:rgb(94, 129, 172);">autoID(true)</font>`<font style="color:rgb(26, 26, 26) !important;">，所以插入时不需要传 </font>`<font style="color:rgb(94, 129, 172);">id</font>`<font style="color:rgb(26, 26, 26) !important;"> 字段，Milvus 会自动生成</font>
+ <font style="color:rgb(26, 26, 26) !important;">向量字段的值是一个 </font>`<font style="color:rgb(94, 129, 172);">Float</font>`<font style="color:rgb(26, 26, 26) !important;"> 的 List，维度必须和 Schema 定义的一致（4096），否则插入会报错</font>
+ <font style="color:rgb(26, 26, 26) !important;">实际项目中，通常会批量插入（比如每次 1000 条），而不是一条一条插。Milvus 对批量插入做了优化，效率更高</font>

<font style="color:rgb(17, 24, 39);">注意，在没有创建索引前，虽然该单元测试显示插入成功，但是 Milvus 控制台查看依然是 0 条数据。只有在创建索引且加载 Collection 到内存时才会正常展示。</font>

### <font style="color:rgb(17, 24, 39);">5. 创建索引</font>
<font style="color:rgb(26, 26, 26) !important;">数据插入之后，还不能直接检索——需要先为向量字段创建索引。没有索引的话，Milvus 只能做暴力搜索，和我们开头说的 MySQL 方案没区别。</font>

```plain
import io.milvus.v2.common.IndexParam;
import io.milvus.v2.service.index.request.CreateIndexReq;

// 为向量字段创建 HNSW 索引
IndexParam vectorIndex = IndexParam.builder()
        .fieldName("vector")
        .indexType(IndexParam.IndexType.HNSW)
        .metricType(IndexParam.MetricType.COSINE)  // 余弦相似度
        .extraParams(Map.of(
                "M", 16,              // 每个向量的最大连接数
                "efConstruction", 256 // 建索引时的搜索宽度
        ))
        .build();

// 为 category 标量字段创建索引（加速过滤查询）
IndexParam categoryIndex = IndexParam.builder()
        .fieldName("category")
        .indexType(IndexParam.IndexType.TRIE)  // 字符串类型用 Trie 索引
        .build();

CreateIndexReq createIndexReq = CreateIndexReq.builder()
        .collectionName("customer_service_chunks")
        .indexParams(List.of(vectorIndex, categoryIndex))
        .build();
client.createIndex(createIndexReq);
System.out.println("索引创建成功");
```

<font style="color:rgb(26, 26, 26) !important;">几个关键参数解释一下：</font>

+ `<font style="color:rgb(94, 129, 172);">IndexType.HNSW</font>`<font style="color:rgb(26, 26, 26) !important;">：我们选 HNSW 作为向量索引，前面分析过，百万级数据量下它是最优选择</font>
+ `<font style="color:rgb(94, 129, 172);">MetricType.COSINE</font>`<font style="color:rgb(26, 26, 26) !important;">：相似度度量用余弦相似度，和上一篇 Embedding 里用的一致。Milvus 还支持 </font>`<font style="color:rgb(94, 129, 172);">L2</font>`<font style="color:rgb(26, 26, 26) !important;">（欧氏距离）和 </font>`<font style="color:rgb(94, 129, 172);">IP</font>`<font style="color:rgb(26, 26, 26) !important;">（内积），后面"实际项目中的关键决策"部分会详细对比</font>
+ `<font style="color:rgb(94, 129, 172);">M = 16</font>`<font style="color:rgb(26, 26, 26) !important;">：每个向量在图中的最大连接数。16 是一个比较通用的值，兼顾了召回率和内存占用</font>
+ `<font style="color:rgb(94, 129, 172);">efConstruction = 256</font>`<font style="color:rgb(26, 26, 26) !important;">：建索引时的搜索宽度，越大索引质量越高但建索引越慢。256 是一个偏高的值，适合对召回率要求较高的场景</font>
+ <font style="color:rgb(26, 26, 26) !important;">标量字段 </font>`<font style="color:rgb(94, 129, 172);">category</font>`<font style="color:rgb(26, 26, 26) !important;"> 用 </font>`<font style="color:rgb(94, 129, 172);">TRIE</font>`<font style="color:rgb(26, 26, 26) !important;"> 索引，适合字符串的等值匹配查询</font>

<font style="color:rgb(26, 26, 26) !important;">索引创建完成后，需要加载 Collection 到内存才能执行检索：</font>

```plain
import io.milvus.v2.service.collection.request.LoadCollectionReq;

client.loadCollection(LoadCollectionReq.builder()
        .collectionName("customer_service_chunks")
        .build());
System.out.println("Collection 已加载到内存");
```

`<font style="color:rgb(94, 129, 172);">loadCollection</font>`<font style="color:rgb(17, 24, 39);"> 会把向量数据和索引加载到内存中。这是 Milvus 的设计——检索是在内存中进行的，所以检索前必须先加载。如果数据量很大，加载过程可能需要一些时间。</font>

### <font style="color:rgb(17, 24, 39);">6. 执行向量检索</font>
<font style="color:rgb(26, 26, 26) !important;">索引建好了，Collection 也加载了，现在可以检索了。模拟一个用户提问：“买了东西不想要了怎么退货？”</font>

```plain
import io.milvus.v2.service.vector.request.SearchReq;
import io.milvus.v2.service.vector.response.SearchResp;

// 用户的问题
String query = "买了东西不想要了怎么退货？";

// 把问题向量化（复用前面的 getEmbeddings 方法）
List<List<Float>> queryVectors = getEmbeddings(List.of(query));

List<BaseVector> milvusQueryVectors = queryVectors.stream()
        .map(FloatVec::new)   // FloatVec(List<Float>)
        .collect(java.util.stream.Collectors.toList());

// 执行向量检索
SearchReq searchReq = SearchReq.builder()
        .collectionName("customer_service_chunks")
        .data(milvusQueryVectors)           // 查询向量
        .topK(3)                      // 返回最相似的 3 个结果
        .outputFields(List.of("chunk_text", "doc_id", "category"))  // 需要返回的字段
        .annsField("vector")          // 指定在哪个向量字段上检索
        .searchParams(Map.of("ef", 128))  // HNSW 检索时的搜索宽度
        .build();

SearchResp searchResp = client.search(searchReq);

// 输出检索结果
List<List<SearchResp.SearchResult>> results = searchResp.getSearchResults();
for (List<SearchResp.SearchResult> resultList : results) {
    System.out.println("=== 检索结果 ===");
    for (int i = 0; i < resultList.size(); i++) {
        SearchResp.SearchResult result = resultList.get(i);
        System.out.println("Top-" + (i + 1) + "：");
        System.out.println("  相似度分数：" + result.getScore());
        System.out.println("  分类：" + result.getEntity().get("category"));
        System.out.println("  文档ID：" + result.getEntity().get("doc_id"));
        System.out.println("  内容：" + result.getEntity().get("chunk_text"));
        System.out.println();
    }
}
```

<font style="color:rgb(26, 26, 26) !important;">检索参数说明：</font>

+ `<font style="color:rgb(94, 129, 172);">topK(3)</font>`<font style="color:rgb(26, 26, 26) !important;">：返回相似度最高的 3 个结果。在 RAG 场景中，通常取 3~10 个，具体取多少取决于你给大模型的上下文窗口有多大</font>
+ `<font style="color:rgb(94, 129, 172);">outputFields</font>`<font style="color:rgb(26, 26, 26) !important;">：指定返回哪些标量字段。不指定的话只返回主键和相似度分数</font>
+ `<font style="color:rgb(94, 129, 172);">searchParams</font>`<font style="color:rgb(26, 26, 26) !important;"> 中的 </font>`<font style="color:rgb(94, 129, 172);">ef = 128</font>`<font style="color:rgb(26, 26, 26) !important;">：HNSW 检索时的搜索宽度。</font>`<font style="color:rgb(94, 129, 172);">ef</font>`<font style="color:rgb(26, 26, 26) !important;"> 越大，召回率越高但检索越慢。一般设置为 </font>`<font style="color:rgb(94, 129, 172);">topK</font>`<font style="color:rgb(26, 26, 26) !important;"> 的 4~16 倍</font>
+ `<font style="color:rgb(94, 129, 172);">annsField("vector")</font>`<font style="color:rgb(26, 26, 26) !important;">：指定在哪个向量字段上做检索。如果 Collection 只有一个向量字段，可以省略</font>

### <font style="color:rgb(17, 24, 39);">7. 结合元数据过滤的混合检索</font>
<font style="color:rgb(26, 26, 26) !important;">纯向量检索有时候不够精确。比如用户问“退货运费谁出？”，你希望只在退货政策类的 chunk 里检索，而不是在物流规则或促销活动里找。这时候就需要在向量检索的基础上加一个标量过滤条件。</font>

<font style="color:rgb(26, 26, 26) !important;">Milvus 支持在检索时通过 </font>`<font style="color:rgb(94, 129, 172);">filter</font>`<font style="color:rgb(26, 26, 26) !important;"> 参数指定过滤表达式，语法类似 SQL 的 Where 子句：</font>

```plain
// 用户的问题
String query = "买了东西不想要了怎么退货？";

// 把问题向量化（复用前面的 getEmbeddings 方法）
List<List<Float>> queryVectors = getEmbeddings(List.of(query));

List<BaseVector> milvusQueryVectors = queryVectors.stream()
        .map(FloatVec::new)   // FloatVec(List<Float>)
        .collect(java.util.stream.Collectors.toList());

// 执行向量检索
// 混合检索：向量相似度 + 标量过滤
// 只在退货政策类的 chunk 里检索
SearchReq filteredSearchReq = SearchReq.builder()
        .collectionName("customer_service_chunks")
        .data(milvusQueryVectors)
        .topK(3)
        .outputFields(List.of("chunk_text", "doc_id", "category"))
        .annsField("vector")
        .filter("category == \"return_policy\"")  // 只搜索退货政策类
        .searchParams(Map.of("ef", 128))
        .build();

SearchResp filteredResp = client.search(filteredSearchReq);

// 输出过滤后的结果
List<List<SearchResp.SearchResult>> filteredResults = filteredResp.getSearchResults();
for (List<SearchResp.SearchResult> resultList : filteredResults) {
    System.out.println("=== 过滤检索结果（仅退货政策） ===");
    for (int i = 0; i < resultList.size(); i++) {
        SearchResp.SearchResult result = resultList.get(i);
        System.out.println("Top-" + (i + 1) + "：");
        System.out.println("  相似度分数：" + result.getScore());
        System.out.println("  内容：" + result.getEntity().get("chunk_text"));
        System.out.println();
    }
}
```

`<font style="color:rgb(94, 129, 172);">filter</font>`<font style="color:rgb(26, 26, 26) !important;"> 表达式支持的语法很丰富，常用的有：</font>

| <font style="color:rgb(26, 26, 26) !important;">表达式</font> | <font style="color:rgb(26, 26, 26) !important;">含义</font> |
| :--- | :--- |
| `<font style="color:rgb(94, 129, 172);">category == "return_policy"</font>` | <font style="color:rgb(26, 26, 26) !important;">等值匹配</font> |
| `<font style="color:rgb(94, 129, 172);">category in ["return_policy", "logistics"]</font>` | <font style="color:rgb(26, 26, 26) !important;">多值匹配</font> |
| `<font style="color:rgb(94, 129, 172);">doc_id != "doc_promo_001"</font>` | <font style="color:rgb(26, 26, 26) !important;">不等于</font> |
| `<font style="color:rgb(94, 129, 172);">category == "return_policy" and doc_id == "doc_return_001"</font>` | <font style="color:rgb(26, 26, 26) !important;">组合条件</font> |


<font style="color:rgb(26, 26, 26) !important;">这种"向量检索 + 标量过滤"的混合检索在 RAG 场景中非常常见。比如：</font>

+ <font style="color:rgb(26, 26, 26) !important;">多租户场景：每个租户只能检索自己的数据，用 </font>`<font style="color:rgb(94, 129, 172);">tenant_id == "xxx"</font>`<font style="color:rgb(26, 26, 26) !important;"> 过滤</font>
+ <font style="color:rgb(26, 26, 26) !important;">权限控制：不同角色能看到的文档不同，用 </font>`<font style="color:rgb(94, 129, 172);">access_level <= 3</font>`<font style="color:rgb(26, 26, 26) !important;"> 过滤</font>
+ <font style="color:rgb(26, 26, 26) !important;">时效性：只检索最近更新的文档，用 </font>`<font style="color:rgb(94, 129, 172);">updated_at > "2026-01-01"</font>`<font style="color:rgb(26, 26, 26) !important;"> 过滤</font>
+ <font style="color:rgb(26, 26, 26) !important;">分类检索：用户明确了问题类别时，缩小检索范围提高精度</font>

## <font style="color:rgb(17, 24, 39);">实际项目中的关键决策</font>
<font style="color:rgb(26, 26, 26) !important;">跑通了 demo，接下来聊聊实际项目中你会遇到的几个关键决策。这些决策没有标准答案，取决于你的数据量、性能要求和资源限制。</font>

### <font style="color:rgb(17, 24, 39);">1. 索引类型怎么选</font>
<font style="color:rgb(26, 26, 26) !important;">前面的“索引算法对比”表格已经给了一个大致的方向，这里再给一个更实操的决策流程：</font>

+ <font style="color:rgb(26, 26, 26) !important;">先问自己：数据量有多大？</font>
    - <font style="color:rgb(26, 26, 26) !important;">< 10 万条：直接用 </font>`<font style="color:rgb(94, 129, 172);">FLAT</font>`<font style="color:rgb(26, 26, 26) !important;">，暴力搜索就够了，省去调参的麻烦</font>
    - <font style="color:rgb(26, 26, 26) !important;">10 万 ~ 500 万条：优先选 </font>`<font style="color:rgb(94, 129, 172);">HNSW</font>`<font style="color:rgb(26, 26, 26) !important;">，速度快、召回率高</font>
    - <font style="color:rgb(26, 26, 26) !important;">500 万 ~ 5000 万条：看内存够不够。够就 </font>`<font style="color:rgb(94, 129, 172);">HNSW</font>`<font style="color:rgb(26, 26, 26) !important;">，不够就 </font>`<font style="color:rgb(94, 129, 172);">IVF_SQ8</font>`<font style="color:rgb(26, 26, 26) !important;">（向量压缩到原来的 1/4）</font>
    - <font style="color:rgb(26, 26, 26) !important;">5000 万条：考虑 </font>`<font style="color:rgb(94, 129, 172);">DISKANN</font>`<font style="color:rgb(26, 26, 26) !important;">（索引放磁盘）或 </font>`<font style="color:rgb(94, 129, 172);">IVF_PQ</font>`<font style="color:rgb(26, 26, 26) !important;">（更激进的压缩）</font>
+ <font style="color:rgb(26, 26, 26) !important;">再问自己：对召回率的要求有多高？</font>
    - <font style="color:rgb(26, 26, 26) !important;">RAG 场景通常取 Top-5 到 Top-10，对召回率的容忍度较高，</font>`<font style="color:rgb(94, 129, 172);">HNSW</font>`<font style="color:rgb(26, 26, 26) !important;"> 和 </font>`<font style="color:rgb(94, 129, 172);">IVF_FLAT</font>`<font style="color:rgb(26, 26, 26) !important;"> 都能满足</font>
    - <font style="color:rgb(26, 26, 26) !important;">如果是人脸识别、指纹匹配等对精度要求极高的场景，可能需要 </font>`<font style="color:rgb(94, 129, 172);">FLAT</font>`<font style="color:rgb(26, 26, 26) !important;"> 或者把 HNSW 的参数调得很大</font>

<font style="color:rgb(26, 26, 26) !important;">对于大多数 RAG 项目，</font>`<font style="color:rgb(94, 129, 172);">HNSW</font>`<font style="color:rgb(26, 26, 26) !important;"> 是默认选择，不需要纠结。</font>

### <font style="color:rgb(17, 24, 39);">2. 相似度度量怎么选</font>
<font style="color:rgb(26, 26, 26) !important;">Milvus 支持三种相似度度量方式：</font>

| <font style="color:rgb(26, 26, 26) !important;">度量方式</font> | <font style="color:rgb(26, 26, 26) !important;">公式直觉</font> | <font style="color:rgb(26, 26, 26) !important;">值域</font> | <font style="color:rgb(26, 26, 26) !important;">越大越相似？</font> | <font style="color:rgb(26, 26, 26) !important;">适用场景</font> |
| :--- | :--- | :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">COSINE（余弦相似度）</font> | <font style="color:rgb(26, 26, 26) !important;">衡量两个向量方向的夹角</font> | <font style="color:rgb(26, 26, 26) !important;">[-1, 1]</font> | <font style="color:rgb(26, 26, 26) !important;">是</font> | <font style="color:rgb(26, 26, 26) !important;">文本语义检索（最常用）</font> |
| <font style="color:rgb(26, 26, 26) !important;">IP（内积）</font> | <font style="color:rgb(26, 26, 26) !important;">衡量两个向量的方向和大小</font> | <font style="color:rgb(26, 26, 26) !important;">(-∞, +∞)</font> | <font style="color:rgb(26, 26, 26) !important;">是</font> | <font style="color:rgb(26, 26, 26) !important;">向量已归一化时等价于余弦</font> |
| <font style="color:rgb(26, 26, 26) !important;">L2（欧氏距离）</font> | <font style="color:rgb(26, 26, 26) !important;">衡量两个向量在空间中的直线距离</font> | <font style="color:rgb(26, 26, 26) !important;">[0, +∞)</font> | <font style="color:rgb(26, 26, 26) !important;">否（越小越相似）</font> | <font style="color:rgb(26, 26, 26) !important;">图像检索、推荐系统</font> |


<font style="color:rgb(26, 26, 26) !important;">怎么选？一个简单的原则：看你用的 Embedding 模型推荐哪种。</font>

+ <font style="color:rgb(26, 26, 26) !important;">大多数文本 Embedding 模型（包括 Qwen3-Embedding-8B、OpenAI text-embedding-3 等）输出的向量已经做了归一化处理，用 </font>`<font style="color:rgb(94, 129, 172);">COSINE</font>`<font style="color:rgb(26, 26, 26) !important;"> 或 </font>`<font style="color:rgb(94, 129, 172);">IP</font>`<font style="color:rgb(26, 26, 26) !important;"> 效果一样</font>
+ <font style="color:rgb(26, 26, 26) !important;">如果不确定模型是否做了归一化，用 </font>`<font style="color:rgb(94, 129, 172);">COSINE</font>`<font style="color:rgb(26, 26, 26) !important;"> 最安全——它会自动处理向量长度的差异</font>
+ `<font style="color:rgb(94, 129, 172);">L2</font>`<font style="color:rgb(26, 26, 26) !important;"> 在文本检索场景中用得较少，更多用在图像、音频等领域</font>

<font style="color:rgb(26, 26, 26) !important;">本系列统一使用 </font>`<font style="color:rgb(94, 129, 172);">COSINE</font>`<font style="color:rgb(26, 26, 26) !important;">。</font>

### <font style="color:rgb(17, 24, 39);">3. 分区策略设计</font>
<font style="color:rgb(26, 26, 26) !important;">Milvus 的 Partition 可以按业务维度把数据分开存储，检索时指定 Partition 可以缩小搜索范围。</font>

<font style="color:rgb(26, 26, 26) !important;">常见的分区策略：</font>

| <font style="color:rgb(26, 26, 26) !important;">分区维度</font> | <font style="color:rgb(26, 26, 26) !important;">示例</font> | <font style="color:rgb(26, 26, 26) !important;">适用场景</font> |
| :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26) !important;">按文档类别</font> | `<font style="color:rgb(94, 129, 172);">return_policy</font>`<font style="color:rgb(26, 26, 26) !important;">、</font>`<font style="color:rgb(94, 129, 172);">logistics</font>`<font style="color:rgb(26, 26, 26) !important;">、</font>`<font style="color:rgb(94, 129, 172);">promotion</font>` | <font style="color:rgb(26, 26, 26) !important;">知识库有明确的分类体系</font> |
| <font style="color:rgb(26, 26, 26) !important;">按租户</font> | `<font style="color:rgb(94, 129, 172);">tenant_001</font>`<font style="color:rgb(26, 26, 26) !important;">、</font>`<font style="color:rgb(94, 129, 172);">tenant_002</font>` | <font style="color:rgb(26, 26, 26) !important;">多租户 SaaS 系统</font> |
| <font style="color:rgb(26, 26, 26) !important;">按时间</font> | `<font style="color:rgb(94, 129, 172);">2026_Q1</font>`<font style="color:rgb(26, 26, 26) !important;">、</font>`<font style="color:rgb(94, 129, 172);">2026_Q2</font>` | <font style="color:rgb(26, 26, 26) !important;">数据有明显的时效性</font> |


<font style="color:rgb(26, 26, 26) !important;">不过，分区不是必须的。在以下情况下，用标量过滤（</font>`<font style="color:rgb(94, 129, 172);">filter</font>`<font style="color:rgb(26, 26, 26) !important;">）替代分区更简单：</font>

+ <font style="color:rgb(26, 26, 26) !important;">分类维度的值很多（比如上百个类别），创建太多 Partition 会增加管理复杂度</font>
+ <font style="color:rgb(26, 26, 26) !important;">查询时经常需要跨多个分类检索</font>
+ <font style="color:rgb(26, 26, 26) !important;">数据量不大（< 100 万），标量过滤的性能开销可以忽略</font>

<font style="color:rgb(26, 26, 26) !important;">一个经验法则：如果某个过滤条件在 90% 以上的查询中都会用到，且值的种类不超过几十个，可以考虑用 Partition；否则用标量过滤就够了。</font>

### <font style="color:rgb(17, 24, 39);">4. 数据更新策略</font>
<font style="color:rgb(26, 26, 26) !important;">知识库不是一成不变的——文档会更新、会删除、会新增。向量数据库里的数据需要和源文档保持同步。</font>

<font style="color:rgb(26, 26, 26) !important;">Milvus 目前不支持原地更新（update）单条数据的向量字段，所以更新的标准做法是删旧插新：</font>

```plain
import io.milvus.v2.service.vector.request.DeleteReq;

// 1. 删除旧数据（通过 doc_id 定位）
DeleteReq deleteReq = DeleteReq.builder()
        .collectionName("customer_service_chunks")
        .filter("doc_id == \"doc_return_001\"")
        .build();
client.delete(deleteReq);

// 2. 对更新后的文档重新分块、向量化

// 3. 插入新数据（同前面的插入流程）
```

<font style="color:rgb(26, 26, 26) !important;">这里 </font>`<font style="color:rgb(94, 129, 172);">doc_id</font>`<font style="color:rgb(26, 26, 26) !important;"> 的作用就体现出来了——它是连接源文档和向量数据库的纽带。当一个文档更新时，通过 </font>`<font style="color:rgb(94, 129, 172);">doc_id</font>`<font style="color:rgb(26, 26, 26) !important;"> 找到这个文档对应的所有 chunk，全部删除，然后重新分块、向量化、插入。</font>

<font style="color:rgb(26, 26, 26) !important;">实际项目中的更新策略通常是这样的：</font>

+ <font style="color:rgb(26, 26, 26) !important;">1.</font>

<font style="color:rgb(26, 26, 26) !important;">源文档变更时，触发一个异步任务</font>

+ <font style="color:rgb(26, 26, 26) !important;">2.</font>

<font style="color:rgb(26, 26, 26) !important;">任务根据 </font>`<font style="color:rgb(94, 129, 172);">doc_id</font>`<font style="color:rgb(26, 26, 26) !important;"> 删除 Milvus 中该文档的所有旧 chunk</font>

+ <font style="color:rgb(26, 26, 26) !important;">3.</font>

<font style="color:rgb(26, 26, 26) !important;">对新文档重新执行 Tika 提取 → 分块 → 向量化 → 插入 Milvus 的完整流程</font>

+ <font style="color:rgb(26, 26, 26) !important;">4.</font>

<font style="color:rgb(26, 26, 26) !important;">整个过程对用户无感知，检索服务不中断</font>

## <font style="color:rgb(17, 24, 39);">小结与下一篇预告</font>
<font style="color:rgb(26, 26, 26) !important;">这一篇我们解决了向量存到哪里的问题。从暴力搜索的性能瓶颈出发，理解了为什么需要专门的向量数据库；学习了 IVF 和 HNSW 两种主流的 ANN 索引算法；对比了市面上的向量数据库方案，选定了 Milvus；最后用 Java 代码跑通了从建表到检索的完整流程。</font>

<font style="color:rgb(26, 26, 26) !important;">到这里，RAG 的离线数据准备链路已经打通了：原始文档 → Tika 提取文本 → 分块 → 元数据管理 → 向量化 → 存入 Milvus。</font>

<font style="color:rgb(26, 26, 26) !important;">但数据准备好只是第一步。当用户真正提问的时候，怎么从 Milvus 里检索出最相关的 chunk？只靠向量相似度够吗？</font>

<font style="color:rgb(26, 26, 26) !important;">答案是：不够。</font>

<font style="color:rgb(26, 26, 26) !important;">纯向量检索有一个天然的短板——它擅长语义匹配，但对关键词匹配不敏感。比如用户问：订单号 2026012345 的物流状态，这里面最关键的信息是订单号，但向量检索可能会忽略这个精确的数字，转而匹配一些语义上“像是在问物流”的 chunk。</font>

<font style="color:rgb(26, 26, 26) !important;">下一篇我们就来解决这个问题：检索策略。会讲到关键词检索（BM25）、混合检索（向量 + 关键词）、以及重排序（Reranking）——这些策略组合起来，才能让 RAG 系统的检索质量真正达到生产可用的水平</font>

## 自检问题
### 为什么需要一个专门的向量数据库来存储向量数据？
我觉得之所以有这么一个问题，是因为我在传统关系数据库中也能实现存储向量数据，比如说创建一个 chunk_vector，里面写一个向量字段和一个文本字段。这样我就能实现对文本的存储，并将其与对应的向量数据关联起来。

但是这样会带来一个问题，那就是我在检索的时候，需要把每行数据全部取出来，在内存中进行相似性计算。这样的话，我们的检索算法就是暴力搜索。

暴力搜索在 demo 阶段是够用的，但是数据量大起来以后，这样检索效率很差，因为它的时间复杂度是 O(n)，而我们的数据可以有几百万往上。

所以我们需要一个专门的数据库来实现这些 ANN 索引，以及专门的一些检索方法。因此向量数据库是向量存储+ANN 索引+高效检索。

### 怎么在传统关系数据库拓展向量功能如 pgvector 与之间做取舍
在传统关系数据库上拓展向量功能的优势是能够维护一个数据库，运维成本低。而缺点则是大数据量的情况下检索性能较差，索引类型不够丰富，以及检索的专项优化相比向量数据库仍有差距。然后这里说的也是向量数据库的优点，缺点则是可能需要维护两套数据库，运维成本更高。
