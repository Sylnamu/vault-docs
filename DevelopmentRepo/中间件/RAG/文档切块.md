### Common Question（QA）
#### 为什么要文档切块
##### x.1 我们不能把整份文档甩给大模型
+ 从**上下文大小**上，一方面 LLM 的上下文窗口有限，我们需要控制上下文的使用：
+ 从**检索精度上**看，资料越多，信息噪声越大，LLM 在提供的大量资料中找到想要的资料就更困难，并且容易把不相关的资料混入回答中。

##### x.2 我们也不能把长文档甩给 Embed 模型
#### 切块为什么重要？
<font style="color:rgb(26, 26, 26);">我们存入的向量数据来自于我们的文本块，分块的质量直接决定了后续检索的质量。块切得好，检索就准；块切得烂，后面怎么优化都救不回来。</font>

### <font style="color:rgb(26, 26, 26);">文档切块策略</font>
#### <font style="color:rgb(17, 24, 39);">1. 固定大小分块（Fixed Size Chunking）</font>
##### <font style="color:rgb(17, 24, 39);">1.1 原理</font>
<font style="color:rgb(26, 26, 26);">这是最简单粗暴的方式：不管文本内容是什么，每隔固定数量的字符就切一刀。</font>

<font style="color:rgb(26, 26, 26);">假设 chunkSize = 100，overlap = 0，上面那段示例文本会被这样切：</font>

+ <font style="color:rgb(26, 26, 26);">块 1：从第 1 个字符开始，取 100 个字符</font>
+ <font style="color:rgb(26, 26, 26);">块 2：从第 101 个字符开始，再取 100 个字符</font>
+ <font style="color:rgb(26, 26, 26);">块 3：从第 201 个字符开始，再取 100 个字符</font>
+ <font style="color:rgb(26, 26, 26);">……依此类推</font>

<font style="color:rgb(26, 26, 26);">用一张图来理解：</font>

</font>

<font style="color:rgb(26, 26, 26);">固定大小分块完全不关心文本的语义——它不管你这一刀切在段落中间还是句子中间，到了字数就切。这既是它的优点（简单），也是它的缺点（可能切断语义）。</font>

##### <font style="color:rgb(17, 24, 39);">1.2 Java 代码实现</font>
```plain
import java.util.ArrayList;
import java.util.List;

public class FixedSizeChunker {

    /**
     * 固定大小分块——最基础的分块方式，按字符数硬切
     */
    public static List<String> chunk(String text, int chunkSize) {
        List<String> chunks = new ArrayList<>();
        int start = 0;
        while (start < text.length()) {
            int end = Math.min(start + chunkSize, text.length());
            chunks.add(text.substring(start, end));
            start = end;
        }
        return chunks;
    }

    public static void main(String[] args) {
        String text = "自签收之日起 7 天内，商品未经使用且不影响二次销售的，"
                + "消费者可申请七天无理由退货。生鲜食品、定制商品、贴身衣物等"
                + "特殊品类不适用此规则，具体以商品详情页标注为准。"
                + "退货运费由消费者承担，如因商品质量问题退货，运费由商家承担。";

        List<String> chunks = chunk(text, 40);

        for (int i = 0; i < chunks.size(); i++) {
            System.out.println("=== 块 " + (i + 1) + " ===");
            System.out.println(chunks.get(i));
            System.out.println();
        }
    }
}
```

<font style="color:rgb(26, 26, 26);">跑一下这段代码，你会看到每个块都是严格的 40 个字符，切割位置完全不考虑句子边界。有些块的开头可能是上一句话的尾巴，读起来很突兀。</font>

##### <font style="color:rgb(17, 24, 39);">1.3 优缺点</font>
| <font style="color:rgb(26, 26, 26);">维度</font> | <font style="color:rgb(26, 26, 26);">说明</font> |
| :--- | :--- |
| <font style="color:rgb(26, 26, 26);">优点</font> | <font style="color:rgb(26, 26, 26);">实现极其简单，性能好，不需要任何 NLP 处理</font> |
| <font style="color:rgb(26, 26, 26);">缺点</font> | <font style="color:rgb(26, 26, 26);">完全忽略文本结构，容易把句子、段落从中间切断，导致语义不完整</font> |
| <font style="color:rgb(26, 26, 26);">适合</font> | <font style="color:rgb(26, 26, 26);">文本结构不重要的场景，比如日志文件、纯数据文本；或者作为其他策略的兜底方案</font> |
| <font style="color:rgb(26, 26, 26);">不适合</font> | <font style="color:rgb(26, 26, 26);">有明确段落结构的文档（知识库、产品手册、政策文件），因为切断语义会严重影响检索质量</font> |

#### <font style="color:rgb(17, 24, 39);">2. 重叠分块（Overlapping Chunking）</font>
##### <font style="color:rgb(17, 24, 39);">2.1 原理</font>
<font style="color:rgb(26, 26, 26);">重叠分块是对固定大小分块的直接改进。核心思路很简单：切块的时候，相邻两个块之间留一段重叠区域，这样即使切割点落在句子中间，重叠部分也能保证关键信息不会被完全切断。</font>

<font style="color:rgb(26, 26, 26);">还是用退货政策那段文本，chunkSize = 100，overlap = 25：</font>

+ <font style="color:rgb(26, 26, 26);">块 1：从第 1 个字符开始，取 100 个字符</font>
+ <font style="color:rgb(26, 26, 26);">块 2：从第 75 个字符开始（100-25=75），取 100 个字符</font>
+ <font style="color:rgb(26, 26, 26);">块 3：从第 150 个字符开始，取 100 个字符</font>
+ <font style="color:rgb(26, 26, 26);">……</font>

<font style="color:rgb(26, 26, 26);">用图来看就是这样：</font>

</font>

<font style="color:rgb(26, 26, 26);">和固定大小分块相比，重叠分块多了一个 overlap 参数，但效果提升明显——边界处的信息不再完全丢失。</font>

##### <font style="color:rgb(17, 24, 39);">2.2 Java 代码实现</font>
```plain
import java.util.ArrayList;
import java.util.List;

public class OverlappingChunker {

    /**
     * 重叠分块——在固定大小的基础上，相邻块之间保留重叠区域
     */
    public static List<String> chunk(String text, int chunkSize, int overlap) {
        if (overlap >= chunkSize) {
            throw new IllegalArgumentException("overlap 必须小于 chunkSize");
        }
        List<String> chunks = new ArrayList<>();
        int step = chunkSize - overlap;
        int start = 0;
        while (start < text.length()) {
            int end = Math.min(start + chunkSize, text.length());
            chunks.add(text.substring(start, end));
            start += step;
        }
        return chunks;
    }

    public static void main(String[] args) {
        String text = "自签收之日起 7 天内，商品未经使用且不影响二次销售的，"
                + "消费者可申请七天无理由退货。生鲜食品、定制商品、贴身衣物等"
                + "特殊品类不适用此规则，具体以商品详情页标注为准。"
                + "退货运费由消费者承担，如因商品质量问题退货，运费由商家承担。";

        List<String> chunks = chunk(text, 40, 10);

        for (int i = 0; i < chunks.size(); i++) {
            System.out.println("=== 块 " + (i + 1) + " ===");
            System.out.println(chunks.get(i));
            System.out.println();
        }
    }
}
```

<font style="color:rgb(26, 26, 26);">对比固定大小分块的代码，核心区别就一行：</font>`<font style="color:rgb(94, 129, 172);">start += step</font>`<font style="color:rgb(26, 26, 26);"> 而不是 </font>`<font style="color:rgb(94, 129, 172);">start = end</font>`<font style="color:rgb(26, 26, 26);">。step = chunkSize - overlap，每次前进的步长比块大小小一点，这样相邻块就自然产生了重叠。</font>

##### <font style="color:rgb(17, 24, 39);">2.3 优缺点</font>
| <font style="color:rgb(26, 26, 26);">维度</font> | <font style="color:rgb(26, 26, 26);">说明</font> |
| :--- | :--- |
| <font style="color:rgb(26, 26, 26);">优点</font> | <font style="color:rgb(26, 26, 26);">实现简单，有效缓解边界处的语义断裂问题</font> |
| <font style="color:rgb(26, 26, 26);">缺点</font> | <font style="color:rgb(26, 26, 26);">仍然不看文本内容，只是用重叠来弥补；overlap 会导致存储量增加</font> |
| <font style="color:rgb(26, 26, 26);">适合</font> | <font style="color:rgb(26, 26, 26);">大多数通用场景的入门方案，尤其是你还没确定用什么策略的时候</font> |
| <font style="color:rgb(26, 26, 26);">不适合</font> | <font style="color:rgb(26, 26, 26);">对语义完整性要求很高的场景，比如法律条款、合同文本</font> |


#### <font style="color:rgb(17, 24, 39);">3. 递归分块（Recursive Chunking）</font>
##### <font style="color:rgb(17, 24, 39);">3.1 原理</font>
<font style="color:rgb(26, 26, 26);">递归分块是目前实践中最常用的策略。它的思路可以用一句话概括：先尝试用最大的分隔符切，切完如果某个块还是太大，就换一个更小的分隔符继续切，直到所有块都在 chunkSize 以内。</font>

<font style="color:rgb(26, 26, 26);">具体来说，它维护一个分隔符列表，按优先级从高到低排列，比如：</font>

```plain
["\n\n", "\n", "。", "，", " ", ""]
```

<font style="color:rgb(26, 26, 26);">切割过程是这样的：</font>

</font>

<font style="color:rgb(26, 26, 26);">这个先粗后细的过程就是递归的含义——不是一刀切到底，而是逐层细化。</font>

<font style="color:rgb(26, 26, 26);">为什么这种方式好？因为它尽最大努力保留文本的结构。能按段落切就按段落切，段落太长了才按句子切，句子还太长才按逗号切……只有在万不得已的时候才会像固定大小分块那样按字符硬切。</font>

<font style="color:rgb(26, 26, 26);">拿我们的电商知识库来说，如果 chunkSize 设成 200，递归分块会先尝试按章节（空行）切割。退货政策那一段大约 150 字，没超过 200，就完整保留为一个块。如果某个章节特别长超过了 200 字，才会进一步按句号切成更小的块。</font>

##### <font style="color:rgb(17, 24, 39);">3.2 优缺点</font>
| <font style="color:rgb(26, 26, 26);">维度</font> | <font style="color:rgb(26, 26, 26);">说明</font> |
| :--- | :--- |
| <font style="color:rgb(26, 26, 26);">优点</font> | <font style="color:rgb(26, 26, 26);">兼顾了语义完整性和块大小控制，是目前最通用的分块策略</font> |
| <font style="color:rgb(26, 26, 26);">缺点</font> | <font style="color:rgb(26, 26, 26);">分隔符列表需要根据语言调整（中文和英文的标点不同）；依赖文本中存在合理的分隔符</font> |
| <font style="color:rgb(26, 26, 26);">适合</font> | <font style="color:rgb(26, 26, 26);">绝大多数场景，尤其是你不确定该用什么策略的时候，递归分块是最安全的默认选择</font> |
| <font style="color:rgb(26, 26, 26);">不适合</font> | <font style="color:rgb(26, 26, 26);">对分块有特殊要求的场景，比如代码文件（需要按函数/类来切）、表格数据（需要按行来切）</font> |


#### <font style="color:rgb(17, 24, 39);">4. 语义分块（Semantic Chunking）</font>
##### <font style="color:rgb(17, 24, 39);">4.1 原理</font>
<font style="color:rgb(26, 26, 26);">前面三种策略有一个共同的局限：它们都是基于规则的——要么按字数切，要么按标点符号切。它们不理解文本在说什么。</font>

<font style="color:rgb(26, 26, 26);">语义分块换了一个完全不同的思路：用 Embedding 模型来判断文本的语义相似度，在语义发生明显变化的地方切割。</font>

<font style="color:rgb(26, 26, 26);">具体过程是这样的：</font>

+ <font style="color:rgb(26, 26, 26);">1.先把文本按句子拆开（这一步可以简单地按句号切）</font>
+ <font style="color:rgb(26, 26, 26);">2.对每个句子生成一个向量（Embedding）</font>
+ <font style="color:rgb(26, 26, 26);">3.计算相邻句子之间的向量相似度</font>
+ <font style="color:rgb(26, 26, 26);">4.当相邻句子的相似度低于某个阈值时，说明话题发生了转换，在这里切一刀</font>

</font>

<font style="color:rgb(26, 26, 26);">还是用电商知识库的例子。退货政策那一段里，前两句都在讲退货条件，它们的语义向量会比较接近，相似度高。但从退货政策的最后一句过渡到换货政策的第一句时，话题发生了明显变化，两个句子的向量相似度会骤降——语义分块就在这个位置切一刀。</font>

<font style="color:rgb(26, 26, 26);">这种方式的好处是显而易见的：它切出来的每个块在语义上是高度内聚的，不会出现一个块里混着两个不相关话题的情况。</font>

<font style="color:rgb(26, 26, 26);">相比 Embedding 计算相似度的方式，直接让大模型来做分块决策更加直观——大模型本身就具备强大的语义理解能力，可以直接读懂文本，判断哪里应该切分。</font>

<font style="color:rgb(26, 26, 26);">最直接的思路：把文本交给大模型，让它找出主题切换的位置。</font>

<font style="color:rgb(26, 26, 26);">对比 Embedding vs LLM 分块：</font>

| <font style="color:rgb(26, 26, 26);">维度</font> | <font style="color:rgb(26, 26, 26);">Embedding 语义分块</font> | <font style="color:rgb(26, 26, 26);">LLM 辅助分块</font> |
| :--- | :--- | :--- |
| **<font style="color:rgb(17, 24, 39);">原理</font>** | <font style="color:rgb(26, 26, 26);">计算相邻句子的向量相似度</font> | <font style="color:rgb(26, 26, 26);">大模型直接理解文本语义</font> |
| **<font style="color:rgb(17, 24, 39);">分块质量</font>** | <font style="color:rgb(26, 26, 26);">依赖 Embedding 模型质量</font> | <font style="color:rgb(26, 26, 26);">通常更准确，能处理复杂语境</font> |
| **<font style="color:rgb(17, 24, 39);">速度</font>** | <font style="color:rgb(26, 26, 26);">快（毫秒级）</font> | <font style="color:rgb(26, 26, 26);">慢（秒级）</font> |
| **<font style="color:rgb(17, 24, 39);">成本</font>** | <font style="color:rgb(26, 26, 26);">低</font> | <font style="color:rgb(26, 26, 26);">高</font> |
| **<font style="color:rgb(17, 24, 39);">适用场景</font>** | <font style="color:rgb(26, 26, 26);">大批量文档处理</font> | <font style="color:rgb(26, 26, 26);">高价值文档、需要精细分块</font> |


##### <font style="color:rgb(17, 24, 39);">4.2 优缺点</font>
| <font style="color:rgb(26, 26, 26);">维度</font> | <font style="color:rgb(26, 26, 26);">说明</font> |
| :--- | :--- |
| <font style="color:rgb(26, 26, 26);">优点</font> | <font style="color:rgb(26, 26, 26);">切割点基于语义而非规则，分块质量最高，每个块的主题高度内聚</font> |
| <font style="color:rgb(26, 26, 26);">缺点</font> | <font style="color:rgb(26, 26, 26);">需要调用 Embedding 或者 Chat 模型，有额外的计算成本和延迟；阈值需要调参；对模型的质量有依赖</font> |
| <font style="color:rgb(26, 26, 26);">适合</font> | <font style="color:rgb(26, 26, 26);">对检索精度要求很高的场景，比如法律文档问答、医疗知识库、金融合规文档</font> |
| <font style="color:rgb(26, 26, 26);">不适合</font> | <font style="color:rgb(26, 26, 26);">文档量特别大且对延迟敏感的场景；文本本身结构已经很清晰的场景（用递归分块就够了，没必要上语义分块）</font> |


##### 
#### <font style="color:rgb(17, 24, 39);">5. 混合分块（Hybrid Chunking）</font>
##### <font style="color:rgb(17, 24, 39);">5.1 原理</font>
<font style="color:rgb(26, 26, 26);">实际项目中，单一的分块策略往往不够用。不同类型的文档、甚至同一份文档的不同部分，可能适合不同的分块方式。混合分块的思路就是：把多种策略组合起来用，取长补短。</font>

<font style="color:rgb(26, 26, 26);">常见的组合方式有几种：</font>

<font style="color:rgb(26, 26, 26);">第一种，递归分块 + 语义分块。先用递归分块做粗切，把文本按段落、章节切成大块；然后对每个大块再用语义分块做细切，确保每个最终的块在语义上是内聚的。</font>

![无法获取该图片](https://cdn.nlark.com/yuque/0/2026/png/52071075/1791268649316-4b9a6c2a-3320-4db3-aa99-e08a72e54d37.png)<font style="color:rgb(26, 26, 26);">  
</font>

<font style="color:rgb(26, 26, 26);">第二种，按文档类型选策略。比如在一个企业知识库系统中，产品手册用递归分块，FAQ 用按问答对切割，合同文本用语义分块。在代码层面，就是一个路由逻辑，根据文档的类型或来源选择不同的分块器。</font>

<font style="color:rgb(26, 26, 26);">第三种，分块 + 后处理。先用递归分块切完，然后对结果做一轮后处理：合并太短的块、拆分太长的块、给每个块补充元数据（比如所属章节标题、文档来源）。</font>

<font style="color:rgb(26, 26, 26);">拿我们的电商知识库来说，一个实际的混合方案可能是这样的：</font>

+ <font style="color:rgb(26, 26, 26);">知识库正文（退货政策、物流规则等）：用递归分块，按章节切割</font>
+ <font style="color:rgb(26, 26, 26);">FAQ 问答对：按问答对切割，每个 Q&A 是一个块</font>
+ <font style="color:rgb(26, 26, 26);">商品详情页：先提取结构化字段（价格、规格），再对描述文本用重叠分块</font>

##### <font style="color:rgb(17, 24, 39);">5.2 优缺点</font>
| <font style="color:rgb(26, 26, 26);">维度</font> | <font style="color:rgb(26, 26, 26);">说明</font> |
| :--- | :--- |
| <font style="color:rgb(26, 26, 26);">优点</font> | <font style="color:rgb(26, 26, 26);">灵活，能针对不同内容选择最合适的策略，整体效果最好</font> |

### 文档切块要点
+ **避免固定长度硬切：** 固定长度分块容易切断句子或语义，应优先采用基于语义边界（如段落、标题）的递归分割。
+ **语义分块 (Semantic Chunking):** 基于句子级别的嵌入（Embedding）相似度进行切分。当相邻句子的语义相似度低于某个阈值时，在此处进行分割，以保持块内语义的完整性。	
+ **设置重叠 (Overlap):** 在相邻的文本块之间设置 10%-20% 的重叠区域（例如 50-200 tokens），可以有效缓解因切分导致的信息截断问题，保持上下文连贯性。
+ **调整块大小 (Chunk Size):** 根据场景动态调整。短文档或问答场景可使用 256-512 tokens，长文档或摘要场景可使用 512-1024 tokens。

#### <font style="color:rgb(17, 24, 39);">2. chunkSize 和 overlap 的经验值参考</font>
<font style="color:rgb(26, 26, 26);">这些不是标准答案，而是社区实践中比较常见的起始值，你可以在此基础上根据实际效果调整：</font>

| <font style="color:rgb(26, 26, 26);">参数</font> | <font style="color:rgb(26, 26, 26);">推荐范围</font> | <font style="color:rgb(26, 26, 26);">说明</font> |
| :--- | :--- | :--- |
| <font style="color:rgb(26, 26, 26);">chunkSize</font> | <font style="color:rgb(26, 26, 26);">200 ~ 1000 字符</font> | <font style="color:rgb(26, 26, 26);">问答场景偏小（200500），摘要场景偏大（5001000）</font> |
| <font style="color:rgb(26, 26, 26);">overlap</font> | <font style="color:rgb(26, 26, 26);">chunkSize 的 10% ~ 25%</font> | <font style="color:rgb(26, 26, 26);">比如 chunkSize=500 时，overlap 设 50~125</font> |


<font style="color:rgb(26, 26, 26);">一个实用的调参思路：从 chunkSize=500、overlap=50 开始，跑几个测试 query 看检索效果，如果发现检索结果不够精准就调小 chunkSize，如果发现上下文经常断裂就调大 overlap。</font>

#### <font style="color:rgb(17, 24, 39);">3. 企业级解决方案</font>
<font style="color:rgb(26, 26, 26);">真实项目里，分块效果不好，往往不只是 </font>`<font style="color:rgb(94, 129, 172);">chunkSize</font>`<font style="color:rgb(26, 26, 26);"> 没调对，还有可能是</font>**<font style="color:rgb(17, 24, 39);">上游抽取出来的文本就已经“脏”了</font>**<font style="color:rgb(26, 26, 26);"> ——尤其是 PDF 这种格式：</font>

+ <font style="color:rgb(26, 26, 26);">页眉页脚、目录、页码混进正文，语义被大量噪音稀释</font>
+ <font style="color:rgb(26, 26, 26);">断行/连字把一句话拆成多段，导致按段落/句子递归分割失效</font>
+ <font style="color:rgb(26, 26, 26);">表格被打散成碎词或错位字段，检索命中但无法形成可读上下文</font>

<font style="color:rgb(26, 26, 26);">所以通常不会“抽完就切”。更稳妥的流程是：</font>**<font style="color:rgb(17, 24, 39);">先用Tika等工具做文本抽取→再用清洗器做结构修复与去噪→最后才进入分块与向量化</font>**<font style="color:rgb(26, 26, 26);"> 。</font>

<font style="color:rgb(26, 26, 26);">分块层面也有类似的现实问题。像 Dify、RAGFlow 这类标准 RAG 方案，很多时候依赖单一分块策略，调参就容易出现“顾此失彼”：</font>`<font style="color:rgb(94, 129, 172);">chunkSize</font>`<font style="color:rgb(26, 26, 26);"> 调大，A 类问题更容易召回完整上下文，但 B 类问题的检索精度可能下降；</font>`<font style="color:rgb(94, 129, 172);">chunkSize</font>`<font style="color:rgb(26, 26, 26);"> 调小，B 类问题更精准了，A 类问题又容易被切断。</font>

<font style="color:rgb(26, 26, 26);">针对</font>**<font style="color:rgb(17, 24, 39);">中小规模文档</font>**<font style="color:rgb(26, 26, 26);"> ，更实用的做法是：先用基础策略把文档拆成初稿块，然后在此基础上做一轮</font>**<font style="color:rgb(17, 24, 39);">人工二次编排</font>**<font style="color:rgb(26, 26, 26);"> ——根据相邻块的语义关系进行补齐、合并或重分配，让最终的 chunk 更贴合真实问题类型。</font>
